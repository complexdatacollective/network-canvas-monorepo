# Studio #1252 outbox dispatcher integration audit

**Audit baseline:** `3911af1a35ff358f930dfa91c671ce27fa1e5d76`

**Question:** Does every outbox named by [#1252](https://github.com/complexdatacollective/network-canvas-monorepo/issues/1252) run through the shared dispatcher and therefore emit its shared lifecycle metrics?

## Verdict

No. Two of the six named consumer domains are live through the shared dispatcher: team invitations and audit alerts. Those are two of the seven queue labels because rollup recompute is represented by separate wave and stage tables. Audit exports, message deliveries, webhook deliveries, and both rollup worklists have metric-query shapes but no production dispatcher adapter or worker startup. Message, webhook, and rollup rows also have no production producer in this tree.

The exhaustive `OutboxQueue` union and queue probe must not be treated as evidence that a consumer is integrated. `apps/studio/server/src/outbox/instrumentation.ts:1-9` declares all seven labels, while `apps/studio/server/src/observability/queues.ts:18-71` supplies direct SQL for all seven tables. The probe reads the tables independently at scrape time (`queues.ts:113-135`). Only a running `OutboxDispatcher` emits dispatch, heartbeat, and worker lifecycle events through the observer (`apps/studio/server/src/outbox/dispatcher.ts:273-289`; `apps/studio/server/src/outbox/worker.ts:32-60`).

The storage is intentionally ahead of the runtime in several places:

- Audit export jobs already carry high-water, availability, lease, status, failure, artifact, and single-use-handle fields in `apps/studio/server/src/audit/schema.ts:162-290`.
- Message deliveries already carry attempt, lease, terminal, provider, suppression, payload-hash, and callback-event storage in `apps/studio/server/src/schedule/schema.ts:369-525`.
- Webhook deliveries already carry Standard Webhooks identity, thin bounded payload, attempt, lease, and terminal fields in `apps/studio/server/src/webhook/schema.ts:115-181`.
- Rollups expose only `stale_at` and `recomputed_at`, with no lease, attempt, or terminal state (`apps/studio/server/src/monitoring/schema.ts:28-77` and `79-121`). The queue probe acknowledges that distinction at `apps/studio/server/src/observability/queues.ts:18-20`.

### Incoming Registry intent integration

The not-yet-integrated Registry flow checkpoint `d139158df97fd9db97894cb979051f28cacdb21c` adds durable publication and import intent tables. It combines them into one `template_registry_intents` metric label, but its `apps/studio/server/src/template/registry-intent-worker.ts:31-214` independently implements maintenance-role verification, a cross-table claim, lease renewal, and retry deferral without emitting through the shared worker observer. This is additional integration work rather than one of #1252's original six named domains.

The parent integration must retain the domain-specific atomic selection across both intent tables and its factual completion/defer behavior, while driving polling through `startOutboxWorker` and emitting the shared lifecycle observations under `template_registry_intents`. No second polling loop or copied worker-error path should ship. Add the Registry intent label to the closure invariant below when the checkpoint is merged.

## Shared-engine prerequisite

The current engine assumes that every successful `deliver()` is an external handoff: if `recordComplete()` fails, it calls `recordUncertain()` and prevents an ordinary retry (`apps/studio/server/src/outbox/dispatcher.ts:244-270`). That is correct for an email, SMS, or webhook whose provider may have accepted the request. It is not correct for retry-safe internal recomputation, deterministic export work, or the existing in-app audit-alert path.

The in-app case is already reachable. `AuditAlertDeliveryAdapter.deliver()` performs no external handoff for `channel = 'in_app'` (`apps/studio/server/src/audit/alert-delivery.ts:244-295`), but a transient `recordComplete()` failure still sends that delivery to `uncertain_at` (`alert-delivery.ts:342-361`). Before adding internal workers, add an adapter-provided completion-failure disposition so an adapter can distinguish ambiguous provider acceptance from retry-safe finalization. Prove the change with a PostgreSQL regression in which in-app completion fails once and is later completed, while an accepted email remains terminally uncertain.

## Minimum separately reviewable implementation slices

1. **Dispatcher completion semantics (#1252).** Add the adapter-owned completion-failure disposition described above and the live in-app regression. Keep the existing lease-owner compare-and-set, heartbeat, backoff, suppression, and external-provider uncertainty behavior.

2. **Staged audit-export backend (#1520).** Add the bounded direct/staged decision and RPC contract, atomically enqueue the staged job with `audit.export.started`, generate only through `sequence <= highWater` into private storage, and run the adapter from the shared worker startup. Publish the actor/team-bound single-use handle only in the short audited completion transaction; delete partial artifacts and record `audit.export.failed` on failure. This is the smallest #1520 slice that creates a real producer and consumer; the activity UI can remain a separate review.

3. **Webhook runtime (#1291).** Add an authenticated subscription/event producer and a Standard Webhooks 1.0.0 sender adapter using the existing thin payload and leased secret-read authority. Start it through the common worker, preserve `webhook-id` across retries, classify post-request ambiguity as uncertain, and audit delivery. A schema-only queue plus the synthetic qualification request is not production delivery.

4. **Message delivery infrastructure (#1305).** Reuse `EmailSender`, add the `SmsSender` port and configured provider adapters, resolve addresses through the audited PII path, recheck blind-index suppression inside the claim, handle authenticated provider callbacks, and start the shared worker. The worker can be reviewed separately from schedule UI, but #1252 cannot claim a reachable message consumer until #1304/#1306 supply a production occurrence/message enqueue path. Preserve the per-participant advisory lock and bounded, jittered provider concurrency required by #1305.

5. **Real rollup worklist (#1268).** First land real session and per-stage timing input; #1268 records that the current per-stage seed is fictional and depends on #1646. Add transactional stale marking and persistent claim state, either as lease/attempt columns or a separate recompute-job table, before adapting recomputation to the shared worker. Do not model a bare `stale_at` row as safely claimed work and do not qualify the seed as a production populator.

6. **Closure invariant (#1252).** Replace the current type-only inventory with an exhaustive production worker registry, or an equivalent exhaustive test, that binds each `OutboxQueue` label to a runtime-started adapter or shared worker. In real PostgreSQL tests, enqueue one job through each production producer and assert shared dispatch/heartbeat/error observations. Include the incoming combined `template_registry_intents` label after its parent merges. This prevents queue-probe coverage from getting ahead of live consumers again.

## Qualification limit

The present metrics endpoint can report depth and age for every named table, but four domains cannot emit shared dispatch-result, heartbeat, or worker-error metrics because no corresponding worker exists. #1252's every-outbox acceptance criterion remains open until slices 1-6 land and the production enqueue-to-dispatch paths are exercised.

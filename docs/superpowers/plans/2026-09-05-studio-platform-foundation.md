## Review and verification

Each implementation runs in an isolated feature worktree with user commit attribution. The orchestrator reviews complete diffs and dependency interactions before delivery. A second agent performs adversarial review; implementation authors address confirmed findings and prove new security/data-preservation assertions can fail. Required types, lint, Knip, schema guards, focused tests, and selected CI/E2E checks must pass before merging.

Database integration suites must use isolated database names/instances or run serially; fixed-name Studio Sync suites can collide across worktrees. Generated schema artifacts are reviewed and regenerated with the migration that owns their change. Rendered changes use the Network Canvas UI skill and visual-baseline policy; unrelated app baselines are not rewritten.

Particular failure cases to review:

- Untrusted request IDs, raw URL paths, exception messages, or metric labels leaking identifiers or secrets.
- Role settings that look correct on `studio_app` but do not apply when the login switches to that role. Verify `SHOW work_mem` through the actual app pool.
- Duplicate external sends after ambiguous acceptance, process death, lease loss, or partial multi-recipient delivery.
- Bootstrap races, invitation bypasses, secret configuration persisted by setup, or setup reappearing after restart.
- Migration sidecars changing privileges or fingerprints without a versioned upgrade path.
- Healthy liveness hiding failed readiness; readiness calls hanging or making external telemetry calls.
- A managed CDN client-only release restarting the backend; a composite self-host client-only update that skips the documented drain/reconnect and downtime qualification; discarding old hashed client assets needed by open editors; multiple WebSocket replicas; schema migrations running on ordinary deploy; or rollback selecting an incompatible image.
- Migration promotion must either prove expand/contract compatibility with both adjacent backend versions or block new admission, drain and stop all web/worker processes, apply the migration, start the compatible image, pass smoke tests, and only then reopen admission and worker egress. Apply the same compatibility check to rollback; an announced window alone does not stop old writers.
- Backups that restore rows without usable historical keys or referenced object bytes, share the primary provider's failure domain, or have never been restored.

## Operational decisions and pending qualification

- Proposed migration window: Tuesdays **15:00–16:00 UTC**, announced in advance. This overlaps US and South African working hours and leaves several working days for follow-up. Routine compatible code releases can occur outside this window.
- Operator alert channel: configure `info@networkcanvas.com`, the project-owned address already published in `SECURITY.md`. This gives the small operating team one established incident destination without another paid notification service. Send through the monitoring system's own transport and credentials, independent of both Studio's dispatcher and its configured mail provider or SMTP endpoint. Operator recipients are separate from participant/researcher recipients. Confirm mailbox ownership and prove routing still works with the Studio dispatcher stopped and its mail provider unavailable; use a synthetic receiver for qualification before enabling the real destination.
- Managed logs and metrics: 30 days, with participant identifiers and payloads excluded. Managed residency: one US region; the identical self-host artifact is the alternative for other residency needs.
- Database recovery scope: every provisioned Studio and registry database, in production and staging, must independently meet the following PITR, independent-dump, retention, monitoring, and initial/quarterly restore criteria. Keep an inventory keyed by database identity so success for one database cannot hide an omitted database or its stale recovery stream.
- Provider PITR target: RPO ≤5 minutes and RTO ≤4 hours, verified by an initial and then quarterly recorded restore drill for each database. Retain at least seven days of continuous recovery points. Poll each database's latest restorable checkpoint and PITR-enabled state every minute, using bounded requests; alert at four minutes of recovery lag, disabled PITR, or an unavailable/stale monitor result. Verify this against a stopped recovery stream as well as an idle database. A provider that cannot expose or otherwise prove a continuously monitored latest restorable point does not pass qualification; generic database health or the timestamp of a daily backup is insufficient. Recover databases with their complete required external key configuration, including PII encryption, integration encryption, and the stable blind-index key. Wrong-key and missing-key controls for each purpose must refuse startup. Independent encrypted logical backups cover primary-provider account loss with their own explicit RPO ≤1 hour and RTO ≤4 hours. Schedule a dump of every database every 30 minutes. For each uploaded generation, read it back from the independent store, authenticate and decrypt it, restore it into an isolated validation database, and verify its complete schema, migration evidence, row counts/content digests, and sequence state against the consistent capture manifest. Advance the recovery checkpoint only after these checks succeed; storage success alone never advances it. Retain every validated-restorable generation for seven days and at least one per day for 30 days. Alert before any database's newest validated-restorable recovery point is an hour old, and measure both targets for every database in an initial and then quarterly second-provider restore drill. Deliberately truncated, modified, undecryptable, and logically incomplete artifacts must fail validation and leave the prior checkpoint unchanged. Include a recovery point at least 29 days old once that history exists, and refuse qualification if any database's retention inventory has gaps. Record these results separately from PITR; a stale dump, omitted database, or restore exceeding either limit fails qualification.
- Object recovery has the same ≤5-minute RPO and ≤4-hour RTO targets. Keep an independent encrypted copy of Studio and registry assets, retaining referenced live content indefinitely and overwritten/deleted versions for at least 31 days and until all retained database recovery points that reference them expire. Advance a recovery-copy checkpoint only after proving completeness against an authenticated authoritative source-version inventory or equivalent reconciled high-watermark and validating every newly copied or changed version through that watermark. Read those versions back from independent storage, authenticate/decrypt them, and verify their bucket/key/version mapping and content hash against the source-bound capture manifest. Reuse durable validation proofs only for unchanged immutable version identities; a fresh checkpoint must include every authoritative version and its valid proof. Account for pagination, concurrent uploads/deletes and deletion markers; an event queue or inventory of already-discovered copies cannot establish completeness. Deliberately drop an upload event before enqueueing: reconciliation must discover the missing version, prevent a falsely fresh checkpoint and alert within the recovery-lag bound. Check the validated checkpoint and pending-version lag every minute; route an operator alert at four minutes so a stopped replicator, failed validation, or missing checkpoint is detected before the RPO is breached. Idle buckets still require a fresh successful authoritative reconciliation; a timestamp-only heartbeat is insufficient. Keep full-history integrity scrubbing separate from checkpoint advancement: use a bounded byte/operation budget with resumable progress to cover every retained version at least once per 30 days, record each version's last successful scrub, and alert on overdue or failed checks. Corruption invalidates its proof, marks affected recovery points unavailable, and triggers repair from a verified source. A checkpoint never rereads the entire historical payload merely to remain fresh. Truncated, corrupted, or mis-mapped copies must preserve the prior validated checkpoint and known-good generations, and must not allow retention cleanup to remove the last recoverable version. Each drill restores the object copy and verifies every restored database asset reference against its content hash; database/key recovery alone is insufficient. Record measured replication lag and recovery times separately from database PITR.
- Independent retention protection: enforce the required database generations, object versions, manifests, and validated checkpoint records with immutable retention in the second provider. Primary-account capture workers receive only the archive recipient public key and append authority. They cannot decrypt archives, advance validated checkpoints, delete or alter retained versions, hide them with deletion markers, shorten retention, bypass object locks, or change lifecycle rules. Keep retention-management and eventual cleanup authority outside the primary account and its secret stores. Recovery selects authenticated immutable version identities, so a new object at an existing key cannot replace a known-good retained version. Use the actual worker credentials to attempt deletion, version deletion, checkpoint removal, retention shortening, and lifecycle changes; every attempt must fail while independently held recovery credentials can still retrieve and restore the known-good generation. Losing the primary account must not give an attacker the means to destroy its independent backups.
- Independent validation boundary: perform archive authentication/decryption, scratch restoration, content comparison, checkpoint signing, and integrity scrubbing on a disposable validator hosted outside the primary account, using independently held recovery/decryption credentials. Use an established asymmetric archive format so primary workers can encrypt to its public recipient without receiving the private recovery key. The validator has no public ingress; its temporary dumps and scratch databases use encrypted ephemeral storage, with egress limited to the required independent storage and alert paths. The research fields remain application-encrypted, and any plaintext recovered for qualification stays inside this boundary. Destroy temporary files, scratch databases, volumes and process credentials after success and every failure path; impose a run deadline and independent orphan cleanup, and prove both cleanup paths. Primary-account loss must leave the validator able to restore the last validated generation without primary credentials. Include this validator, scrub work and recovery reserve in the hosting cost estimate.
- Managed key rotation: annual, with the bounded maintenance re-encryption job proved idempotent. The blind-index key remains stable across encryption-key rotations. Keep the complete external keyset configuration and every referenced root, including a separately configured stable blind-index root and all historical PII and integration roots, in operator-controlled custody independent of the primary hosting account. Retain them until every backup that needs them has expired; removing a key from live writes does not permit destroying it. Exercise a pre-rotation backup with its historical keys and prove restored suppression/blind-index lookups still match. Independently omit and substitute the blind-index, PII, and integration roots to prove each control refuses recovery. The same independent-custody requirement covers every historical dump/object archive encryption and authentication key, second-provider storage recovery credential, and the account-recovery/MFA material needed to use them. Keep recovery credentials and decryption keys outside the primary account, distinct from the worker's live write credentials and outside the data archives themselves. Every independent restore drill must start with all primary-account credentials and secret-store access unavailable, obtain the data and matching keys solely from independent operator custody, and refuse missing or substituted recovery credentials or archive keys. This is operator key backup, consistent with #1258's no-escrow policy.
- Restore into quarantine: keep public web admission and every worker's external side effects disabled until recovery checks finish. A restored database can rewind revocations and delivery terminal states. Invalidate restored sessions and one-time credentials, rotate affected deployment credentials, and reconcile restored account/membership permissions and integration credentials against current trusted operator evidence before reauthorization. Hold all restored delivery queues until provider receipts or other independent evidence resolve possible post-checkpoint sends; ambiguous sends require explicit reconciliation and must never be retried automatically. Test revoked credentials and already-sent deliveries deliberately restored from an earlier recovery point. Neither a current fingerprint nor successful decryption permits automatic reopening.
- End-to-end recovery target: RTO ≤4 hours from recovery invocation until the application and separate registry, their databases, historical keys, objects, routing, and the preceding quarantine/reconciliation steps are complete. End the clock only when authenticated application/registry smoke tests and content-verified restored asset retrieval succeed with safely resumed workers. Keep each component's timing as diagnostic evidence; meeting separate database and object deadlines does not satisfy this overall deadline.
- Required runbooks: deploy/rollback, announced migration window, database failover, object-store outage, dispatcher backlog, key rotation, and security incident. The last links to the repository's disclosure policy. Generate the subprocessor inventory from the estate definition and carry the one-US-region statement into the #1260 subprocessor list and HECVAT Lite handoff.
- A cost estimate must cover the whole estate and satisfy the Postgres tuning, PITR, and independent-backup requirements before provisioning. If the $100 limit cannot satisfy those requirements, report the specific conflict instead of weakening them silently.

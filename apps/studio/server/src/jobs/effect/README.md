# The Effect-native job queue

This directory is the queue that replaces pg-boss for Studio's five background
jobs (`invitation-delivery`, `invitation-delivery-dead-letter`,
`sign-in-email`, `protocol-store-gc`, `denied-attempts-summary`). It lives
beside pg-boss during this phase — both schemas exist in the same database —
and nothing outside this directory calls into it yet; a later stage swaps the
worker program and the command call sites onto it and deletes pg-boss. The
queue's own schema is `studio_jobs`, a dedicated schema separate from
pg-boss's `pgboss` (`packages/studio-sync/src/jobs.ts`'s `JOB_SCHEMA`), so
that a schema push that reconciles `public` never touches either.

It exists for two guarantees.

**The transaction guarantee.** `Jobs.enqueue` (`jobs.ts`) requires the
`Transaction` service, and nothing but `withTransaction` /
`withTenantTransaction` (`database.ts`) provides it. Enqueuing issues one
`INSERT INTO <schema>.jobs`, on the caller's own connection: `SqlClient`
routes every statement by the fiber's `TransactionConnection` service, so
there is no second connection an enqueue could reach for even if it wanted
one. A domain row a command writes and the job it schedules therefore commit
together or not at all — this is the reason the queue exists rather than
Studio keeping pg-boss's own two-pool design. `__tests__/transaction.test.ts`
proves it with three oracles, in increasing strength: rollback and commit
symmetry (failing the transaction body leaves zero domain rows and zero job
rows; letting it finish leaves one of each), the invisibility oracle (while
the caller's transaction is still open, a _second_ connection — a different
pool entirely — reads zero job rows; read-committed isolation means this can
only be true if the insert ran on the first connection, which is what "in the
transaction" means), and same-backend-pid (`pg_backend_pid()` read inside the
transaction, immediately after the domain insert and the enqueue, equals the
pid the domain insert ran on, checked against a third connection's different
pid so the equality cannot be an artefact of a single-connection pool). A
fourth proof is at the type level: `jobs.enqueue(...)` outside a transaction
does not compile (`Effect.runSync` demands `R = never`; `enqueue` leaves
`Transaction` in `R`), asserted with a `@ts-expect-error` so the probe cannot
silently rot into a stale comment. `Jobs.layerRecording` — the fake the domain
command suites use instead of a database — keeps the same requirement, so a
command tested under it is held to the same guarantee it ships with.

**Integration with the planned services.** The queue is built directly on the
`Database` / `Transaction` / `Jobs` / `JobWorker` names and shapes #1927 §4
plans for Studio generally, not a vocabulary of its own — stage 3 reuses these
names rather than inventing a second set. It already depends on one of stage
1's real services: the mail handlers (`handlers/invitation-delivery.ts`,
`handlers/sign-in-email.ts`) send through `Mailer` (`src/mail/mailer.ts`),
whose `sendTeamInvitation` and `sendMagicLink` fail with `MailFailed` or
`MailNotConfigured`. Two other dependencies are not Effect yet — a Valkey rate
limiter and a node-postgres audit writer — and are held behind seams described
in §5 until a later stage moves them.

## 1. Schema

`schema.ts` renders the DDL and grants as two SQL strings,
`jobSchemaSql(schema)` and `jobSchemaGrantsSql(schema)`, both idempotent
(`CREATE ... IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`/`TRIGGER`) so a
schema application that finds `studio_jobs` already installed reapplies it
rather than refusing or dropping it. `assertSchemaName` checks every
interpolated schema name against `/^[a-z_][a-z0-9_]*$/` before it reaches the
DDL string.

### `<schema>.jobs`

| Column                                                           | Purpose                                                                                                                                                                                                                                           |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                                             | `uuid` primary key, `gen_random_uuid()`.                                                                                                                                                                                                          |
| `queue`                                                          | The queue name.                                                                                                                                                                                                                                   |
| `payload`                                                        | `jsonb`, decoded against the queue's Effect Schema on both the enqueue and the claim side (`queues.ts`).                                                                                                                                          |
| `state`                                                          | `created \| active \| completed \| failed \| dead`, default `created`. `dead` is reserved for a payload that no longer decodes — no retry can fix it, so it is distinct from an ordinary `failed` row and a dead-letter copy is never made of it. |
| `policy`                                                         | The queue's policy (`standard` or `singleton`), stamped at enqueue. Stamped rather than looked up because a partial index cannot read a declaration — this column is what `jobs_singleton_active_idx` below is a partial index _over_.            |
| `attempts`                                                       | Incremented by the claim, not after the handler runs, so a process that dies mid-handler still leaves the attempt spent.                                                                                                                          |
| `singleton_key`                                                  | The per-enqueue `singletonKey`, nullable. Unrelated to `policy` — see §2.                                                                                                                                                                         |
| `retry_limit`, `retry_delay`, `retry_backoff`, `retry_delay_max` | The retry policy, frozen onto the row at enqueue (§2). `retry_delay_max` is `null` for "no cap", distinct from a real cap of `0`.                                                                                                                 |
| `expire_in_seconds`                                              | The lease length for one claimed attempt, read off the row at claim time so a job keeps the expiry it was enqueued under.                                                                                                                         |
| `run_at`                                                         | Not claimable before this instant.                                                                                                                                                                                                                |
| `keep_until`                                                     | `run_at + retentionSeconds` at enqueue — pg-boss's `keep_until`: a `created` row nothing ever claims is deleted here rather than retried.                                                                                                         |
| `locked_until`                                                   | Set by the claim to `now + expire_in_seconds`; read by the expiry reaper.                                                                                                                                                                         |
| `last_error`                                                     | The most recent failure message, truncated to 1,000 characters.                                                                                                                                                                                   |
| `outcome`                                                        | What the handler returned: `completed \| suppressed \| uncertain`.                                                                                                                                                                                |
| `dead_letter_of`                                                 | The id of the job this row is a dead-letter copy of, if any.                                                                                                                                                                                      |
| `created_at`, `completed_at`                                     | Self-explanatory.                                                                                                                                                                                                                                 |

### `<schema>.job_schedules`

`name` (primary key), `cron`, `queue`, `payload`, `next_run_at`. One row per
declared cron schedule, upserted by `JobWorker.schedule` so the last replica
to boot with a changed cron expression wins.

### Indexes

| Index                       | Predicate                                                                                         | What it is for                                                                                                                                                                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `jobs_claim_idx`            | `(queue, run_at, created_at) WHERE state = 'created'`                                             | The claim's own lookup.                                                                                                                                                                                                                                                        |
| `jobs_expiry_idx`           | `(locked_until) WHERE state = 'active'`                                                           | The expiry reaper's scan.                                                                                                                                                                                                                                                      |
| `jobs_retention_idx`        | `(queue, completed_at) WHERE state IN ('completed','failed','dead')`                              | The retention pass over terminal rows.                                                                                                                                                                                                                                         |
| `jobs_keep_until_idx`       | `(queue, keep_until) WHERE state = 'created'`                                                     | The retention pass over unclaimed rows.                                                                                                                                                                                                                                        |
| `jobs_singleton_idx`        | UNIQUE `(queue, singleton_key) WHERE singleton_key IS NOT NULL AND state IN ('created','active')` | The per-enqueue `singletonKey`: one job per (queue, key) among live states.                                                                                                                                                                                                    |
| `jobs_singleton_active_idx` | UNIQUE `(queue) WHERE state = 'active' AND policy = 'singleton'`                                  | The `singleton` _policy_: at most one active job per queue. The claim's `NOT EXISTS` guard (worker.ts) is the same rule tried first; this index is the belt that makes the rare race — two workers passing the `NOT EXISTS` together — impossible rather than merely unlikely. |

### The notify trigger

`notify_job()` is a `plpgsql` function that runs `PERFORM
pg_notify('<schema>', NEW.queue)`; `jobs_notify_trigger` fires it `AFTER
INSERT OR UPDATE OF state ON <schema>.jobs FOR EACH ROW WHEN (NEW.state =
'created')`. The channel is the schema's own name (`jobNotifyChannel`), so
production's `studio_jobs` and a suite's scratch sibling never wake each
other's workers, and the payload is the queue name, which is all a worker
needs to release the right poll fiber. `pg_notify` is transactional, so
nothing is announced until the writer's transaction commits — which means
_any_ writer that leaves a row `created` (an enqueue, the expiry reaper
putting a job back, a future node-postgres path, an operator's manual
`UPDATE`) wakes a listening worker with no application code having to
remember to announce it. Because the trigger's body is dollar-quoted
`plpgsql`, every installer that applies this schema must split the DDL with
`splitStatements` (`src/db/statements.ts`), not on `;` — a naive split would
cut the function body in half.

### Grants (`jobSchemaGrantsSql`)

| Role                 | May                                                                                                                                                                                                                                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app` (both)         | `USAGE` on the schema; `INSERT` on `jobs`; `SELECT (id)` on `jobs` — nothing else. This is what the request-serving role needs to create a job and read back its id, and no more: the job table is one table for every team, so a role that could read a payload or the `state` column could read every team's queued work. |
| `maintenance` (both) | `USAGE` on the schema; `ALL` on `jobs` and `job_schedules`.                                                                                                                                                                                                                                                                 |
| Both                 | `EXECUTE` on `notify_job()` — a trigger function runs as the role that fired it, so the application needs this to insert at all.                                                                                                                                                                                            |

`dropJobSchemaSql` is `DROP SCHEMA ... CASCADE`, used by the suites to remove
a scratch schema wholesale.

## 2. Semantics

Every row below states the native queue's behaviour, pg-boss's for
comparison, and the ruling that settled a difference where one exists.

| Aspect                               | This queue                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | pg-boss                                                                                                                                                                                                                                                                                                      | Ruling                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Singleton policy**                 | At most one **active** job per queue; a second job on the same queue is accepted and sits `created` until the first stops being active. Enforced twice: the claim's `AND NOT EXISTS (... WHERE queue = $1 AND state = 'active')` guard tries first, and `jobs_singleton_active_idx` (a partial unique index) makes the rare double-pass impossible rather than unlikely — a unique-violation from that index (`isUniqueViolationCause`, `errors.ts`) is read as "nothing to claim", not as an error.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | The same two-part design: `job_i2`'s partial unique index plus a fetch that tolerates the `23505` two workers can race into.                                                                                                                                                                                 | Match pg-boss: `singleton` never refuses an enqueue, it only bounds how many run at once (brief ruling 1).                                                                                                                                                                                                                                                                                                                                    |
| **Per-enqueue `singletonKey`**       | Unrelated to the policy above: one job per `(queue, key)` among `created`/`active`, enforced by `jobs_singleton_idx`. A collision is `ON CONFLICT DO NOTHING`, surfaced as the typed `JobRefused` error rather than letting the unique index raise `23505` — a raised violation would abort the _caller's_ whole transaction, turning an ordinary "already queued" outcome into the loss of whatever domain work was committing alongside it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | pg-boss's `singletonKey` on `send`.                                                                                                                                                                                                                                                                          | Kept as its own concept, deliberately distinct from the queue-level policy (brief ruling 1).                                                                                                                                                                                                                                                                                                                                                  |
| **Retry policy**                     | Frozen onto the row at enqueue: `retry_limit`, `retry_delay`, `retry_backoff`, `retry_delay_max`, `expire_in_seconds` are copied from the queue's resolved declaration (`queues.ts`) into the INSERT, and every later step — `claim`, `settleFailure`, `reapExpired` — reads the row's own columns, never the live declaration. A redeploy that changes a queue's options therefore changes nothing about a job already in flight. A dead-letter copy freezes the **target** queue's policy at copy time, not the failed job's own — it is a new job on a different queue. `deleteAfterSeconds` is the one exception: it stays queue-level and is read fresh off the declaration at deletion time.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | pg-boss freezes the same five values onto its own row for the same reason, and reads its deletion plan's retention off the live queue the same way.                                                                                                                                                          | Match pg-boss exactly (brief ruling 1).                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Backoff formula**                  | `backoffSeconds` (`worker.ts`): no backoff → `retryDelay` flat; with backoff, `exponent = min(16, attempts)`, `delay = max(retryDelay, 1) * (2^exponent/2 + (2^exponent/2) * roll)` where `roll` comes from the `Random` service (so a test can pin it with `Random.withSeed`), capped by `retryDelayMax` when the queue declares one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | pg-boss 12.31.1 `dist/manager.js:1318-1329`.                                                                                                                                                                                                                                                                 | Copied verbatim.                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Expiry reaper**                    | One statement across every queue at once (`reapExpired`): an `active` row whose `locked_until` has passed goes back to `created` if `attempts <= retry_limit`, or to `failed` otherwise. The attempt was already counted at claim time, so a handler that hangs on every attempt still walks the ladder to its end rather than looping forever.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | pg-boss's own expiry pass.                                                                                                                                                                                                                                                                                   | Matched; one statement rather than pg-boss's per-queue loop because the ladder it compares against now lives on the row.                                                                                                                                                                                                                                                                                                                      |
| **Retention / deletion**             | `deleteExpired`, predicate for predicate against pg-boss's `deletion` plan: a terminal row (`completed`/`failed`/`dead`) is deleted `deleteAfterSeconds` after `completed_at` (`0` keeps it forever); a `created` row nothing ever claimed is deleted once its `keep_until` (`run_at + retentionSeconds` at enqueue) passes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | pg-boss's `plans.deletion`.                                                                                                                                                                                                                                                                                  | Matched (brief ruling 1).                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Dead letter**                      | On the attempt the queue will not retry, if the declaration names a `deadLetter` queue, a new `created` row is inserted on that queue — the same payload, `dead_letter_of` naming the failed job, the **target** queue's own frozen policy — inside the same settling transaction, so a job cannot end up `failed` without its copy existing. Only `invitation-delivery` declares one (`invitation-delivery-dead-letter`; kept forever, 30-day retention).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | pg-boss's own dead-letter copy, and its `createJob` reads the target queue's cached options the same way.                                                                                                                                                                                                    | Matched.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Cron**                             | `schedule`/`tickSchedules` (`worker.ts`) parse every cron expression with `Cron.parse(cron, 'UTC')` — UTC only, no per-schedule timezone. One replica ticks per pass, via `pg_try_advisory_xact_lock(CRON_LOCK_KEY)`, released automatically at commit. Each due schedule enqueues through the same `Jobs.enqueue` a command uses, in the same transaction as the schedule's own advance, **with the schedule's own name as its `singletonKey`** — which bounds a schedule's backlog to one un-finished occurrence.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | pg-boss throttles only the _relay_ job (`__pgboss__send-it`, `singletonSeconds: 60`) and then calls `manager.send` on the target queue, where a `singleton` policy constrains only the _active_ row — so a sweep that runs longer than its cadence can leave pg-boss an unbounded backlog of `created` rows. | Deliberately **not** matched (brief ruling 1's own carve-out): Studio's two scheduled queues (`protocol-store-gc`, `denied-attempts-summary`) are both idempotent whole-world sweeps, where a queued backlog is pure waste and a missed occurrence is picked up by the next tick.                                                                                                                                                             |
| **LISTEN/NOTIFY with poll fallback** | The worker holds one `sql.listen(channel)` for its process life (`forkListener`), reserving one pooled connection — which is why the pool is sized with a connection to spare. Each queue has a `Latch`, starting **open** so a worker that boots onto a backlog drains it immediately rather than waiting out the first poll interval; the poll loop is `race(latch.await, sleep(pollInterval))` then drain-until-idle, and a `NOTIFY` payload opens the matching queue's latch. Default `pollInterval` is **2 s**.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | pg-boss's poll floor is 0.5 s, with no notify mechanism.                                                                                                                                                                                                                                                     | With the trigger in place, polling is now the safety net (a dropped listener connection, a row made `created` while the listener is reconnecting) rather than the primary path, so 2 s rather than pg-boss's 0.5 s floor. Proven in `__tests__/notify.test.ts`, which sets the poll interval to an hour and shows a job settles within 500 ms real time when the listener is on, and is still `created` after the same 500 ms when it is off. |
| **`JobClock` skew correction**       | `clock.ts`. A `Context.Reference` — not a `Context.Service` — whose default is `{ now: DateTime.now }`, the uncorrected Effect `Clock`. Being a reference rather than a service means a program that does not care which clock it gets adds nothing to its requirements, and is exactly what keeps `Jobs.enqueue`'s own requirement at precisely `Transaction`. `JobClock.layer(config?)` (requires `Database`) measures `select now()` against the local clock at build and every `clockMonitorInterval` (default 10 minutes, pg-boss's own default), against the midpoint of the round trip so query latency is not folded into the measured skew, and corrects every subsequent `now` by the difference; a failed measurement keeps the last correction rather than reverting to zero. A program that wants the correction must explicitly provide `JobClock.layer`; anything that provides nothing gets the uncorrected `Clock` (which is what every suite wants, since it is what `TestClock` drives). `JobClock.layerTest` is that same uncorrected clock, named for suites; `JobClock.layerOffset(duration)` is a fixed, non-converging offset for a suite that wants to _be_ the skewed replica rather than to correct one. | pg-boss's `Timekeeper.cacheClockSkew` (`dist/timekeeper.js:229-248`), same interval, and a warning threshold of 60 s (`timekeeper.js:243`), not pg-boss's _own_ documentation value of one second — the code matches the 60 s pg-boss actually uses.                                                         | Match pg-boss's real threshold (brief ruling 1: "read pg-boss's source ... and match it").                                                                                                                                                                                                                                                                                                                                                    |
| **Outcomes and logging**             | A handler returns one of `completed \| suppressed \| uncertain` (`JobOutcome`, `worker.ts`); it never says `retrying` or `failed` — `drainOnce` derives those from the row's own attempt counters after the handler's `Effect` fails: a step that still has retries left is logged with `Effect.logWarning` ("job ... retrying after attempt ..."), one that has none left with `Effect.logError` ("job ... failed on attempt ..."). A successful settle logs at debug. A payload that fails to decode against the queue's schema (`JobPayloadUndecodable`) settles the row to `dead` and logs an error — no ladder applies, since no retry could fix a payload the schema itself rejects.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | pg-boss has no equivalent three-way outcome; success is the absence of a throw.                                                                                                                                                                                                                              | Per #1927 §11.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Graceful stop**                    | `forkBackground`'s finalizer (registered _after_ every recurring fiber is forked, so scope finalizers — which run in reverse — execute it _before_ those fibers are interrupted) sets `fetching = false`, then waits up to `stopTimeout` (default 25 s) for in-flight handlers to drain via the worker's semaphore; if the window elapses it logs a warning and lets the scope interrupt whatever handlers remain. The whole claim-run-settle step in `drainOnce` — not just the handler — holds a semaphore permit, so a stop cannot interrupt a fiber between a handler finishing and its outcome being written.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | pg-boss's own graceful-stop window.                                                                                                                                                                                                                                                                          | Matched in shape.                                                                                                                                                                                                                                                                                                                                                                                                                             |

## 4. Handlers and their seams

Each handler is an `Effect.fn` named `job.<queue>`, taking a decoded
`HandledJob<Queue>` (`worker.ts` decodes the payload against the queue's
schema before a handler ever sees it, so a handler never has to parse).

| File                                  | Replaces                                                                               | Dependencies                                                  | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `handlers/invitation-delivery.ts`     | `src/jobs/handlers/invitation-delivery.ts` + the pg-boss-era dispatcher in `src/team/` | `Database \| Mailer`                                          | Two `withTransaction` calls (count the attempt under `FOR UPDATE ... NOWAIT`; take the invitation again and send). Two of that last handler's dependencies are not Effect yet; each is a
`Context.Service` seam with a live layer wrapping today's Promise
implementation and a test layer beside it, so the handler itself never sees a
`Promise`:

- **`DeniedAttemptsStore`** (`handlers/denied-attempts/store.ts`) wraps
  today's `RateLimitStore` (`src/rate-limit/store.ts`, ioredis). The live
  layer (`DeniedAttemptsStore.layer(store)`) wraps the exact calls the handler
  needs — a cursor `SCAN`, the claim's Lua (`CLAIM_SCRIPT`: rename a live
  window onto its claim key, or extend an existing claim once it has gone
  stale), `discardClaim`, and the scope-count drain (`DRAIN_SCRIPT`) — each in
  `Effect.tryPromise`. `DeniedAttemptsStore.layerAbsent` is what stage 3 wires
  when `REDIS_URL` is unset: `configured: false`, every operation a no-op,
  which is the same posture today's optional `deps.store` takes. A later
  stage (#1927's stage 4) replaces this seam by turning `RateLimitStore`
  itself into an Effect service.
- **`DeniedAuditSummaryWriter`** (`handlers/denied-attempts/audit-writer.ts`)
  wraps today's `createDeniedAuditSummaryWriter`
  (`src/audit/denial-summary.ts`), node-postgres over a `pg.Pool`. The live
  layer takes the **maintenance** pool specifically — a summary is by
  construction a write into a team no request pinned, so it has to run as the
  role allowed to cross tenants. Stage 3 hands this layer the pool it already
  builds; stage 4 replaces the layer with one over the audit store itself and
  this file is deleted.

`handlers/denied-attempts/testing.ts` holds both seams' test doubles beside
the seams themselves rather than inside a suite: `layerMemoryStore` (a `Map`
honouring the claim script's rename/stale-retake semantics exactly, plus
`DeniedAttemptsMemory` for seeding and inspecting it and forcing one operation
to fail), `layerRecordingWriter` / `RecordedSummaries` (records writes,
settable per-call behaviour so a case can fail one write and let the next
succeed), and `layerRefusingWriter` (every write fails — the "the audit log is
gone" case).

## 5. Installing the schema

`install.ts` provides the schema in both shapes a caller needs, sharing one
statement list (`nativeJobSchemaStatements`) so the bytes installed by a
deployment and by a suite's scratch schema cannot drift:

- **`installNativeJobSchema(db: pg.PoolClient, schema: string)`** — the
  node-postgres path, applying `splitStatements(jobSchemaSql(schema))` then
  `splitStatements(jobSchemaGrantsSql(schema))` one statement at a time.
  `splitStatements` (`src/db/statements.ts`) is dollar-quote-aware; a naive
  split on `;` would cut the trigger function's `plpgsql` body in half. Must
  be called inside an existing transaction, same as `installJobSchema` beside
  it for pg-boss — a failure part-way would otherwise leave a schema with only
  some of its tables. The DDL's `IF NOT EXISTS` / `OR REPLACE` idempotence is
  what makes this safe to call on every schema application.
- **`installNativeJobSchemaEffect(schema: string)`** — the same statement list
  over an open `Transaction` (not `Database`, for the same reason
  `Jobs.enqueue` takes `Transaction`: the requirement is what says this runs
  inside a transaction someone else opened), for a worker that owns its own
  `Database` and creates the schema through `withTransaction`.

There is no version stamp of the queue's own: the DDL strings feed into
Studio's overall `SCHEMA_FINGERPRINT`, so a change to either function is a
stale database like any other, caught by the same fingerprint check every
other sidecar goes through.

The suites' own harness (`__tests__/support.ts`) reuses the exact same
statements. `layerQueueHarness` builds a scratch schema named
`studio_test_<uuid>` per suite, applies `jobSchemaSql` +
`jobSchemaGrantsSql` through the owner identity inside a transaction, and
drops it via `dropJobSchemaSql` in a layer finalizer.
`layerDeliveryHarness` — for suites whose handlers read both Studio's own
tables and the job queue — additionally provisions a full Studio scratch
schema through the existing `src/__tests__/support/postgres.ts` helpers and
installs the queue into a `<studioSchema>_ejobs` sibling schema, named so the
`studio_test_%` sweep in `scripts/apply.ts` reclaims it after a crashed run,
the same convention pg-boss's own scratch schema follows.

**pg-boss's data is not migrated.** `studio_jobs` is created empty. When a
later stage switches production callers onto this queue, whatever is sitting
in pg-boss's `pgboss` schema is discarded, not carried over — there is
nothing in this directory that reads a pg-boss row.

## 6. What a later stage must wire to switch production onto it

This phase deliberately does not touch any of: `src/programs/*`,
`src/index.ts`, `src/worker.ts`, `src/migrate.ts`, the pg-boss modules
(`src/jobs/{client,enqueue,worker,registrations,install,database,log}.ts`,
`src/jobs/handlers/*`), `src/mail/*`, the compose files, or `src/team/**` —
pg-boss keeps running in the image until that stage swaps the worker program
and every command call site onto this queue. That switch has to:

- **Build the worker program's layer graph.** Compose `JobWorker.layer(...)`
  over `Jobs.layer(...)`, `Database.layer('maintenance', ...)`, and
  `JobClock.layer(...)` (the production skew correction, not
  `JobClock.layerTest`/`layerOffset`, which are test-only) — the same shape
  `__tests__/support.ts`'s `layerWorker` composes for the suites, but with
  `background: true` and the live clock.
- **Swap the command call sites.** Wherever a command currently sends a job
  through pg-boss (the invitation-delivery and sign-in-email sends in
  `src/team/**` and elsewhere), call `Jobs.enqueue` inside the same
  `withTransaction`/`withTenantTransaction` the domain write already runs in,
  and provide `Jobs.layerRecording` under the domain command suites instead of
  the live layer.
- **Provide `JobClock.layer`.** The production worker measures its skew
  against its own `Database`'s `now()` rather than running on the uncorrected
  `Clock` the suites use.
- **Add the metrics layer beside readiness.** Mount `JobQueueMetrics.layer()`
  in the same place `jobsCheck(worker, maintenanceDatabase)` is registered
  into the process's `HealthChecks`, so both the gauges and the readiness
  probe come from the one `queueDepths` pass.
- **Decide the mail-transport registration.** `sign-in-email.ts`'s own comment
  names this explicitly: whether the worker calls `worker.work` for
  `invitation-delivery` / `sign-in-email` at all has to depend on whether a
  mail transport is actually configured (`Mailer.layerConsole` /
  `Mailer.layerRefuse` or an equivalent check), so a deployment with no SMTP
  set up does not burn a queued send's whole retry ladder before an operator
  finishes configuring it.
- **Delete the pg-boss modules** once nothing calls them: exactly
  `src/jobs/client.ts`, `src/jobs/enqueue.ts`, `src/jobs/worker.ts`,
  `src/jobs/registrations.ts`, `src/jobs/install.ts`, `src/jobs/database.ts`,
  `src/jobs/log.ts`, and every file under `src/jobs/handlers/*` — each one
  superseded by a module under this directory.

## 7. Testing

| Harness module                  | What it provides                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `__tests__/support.ts`          | `QueueHarness` / `layerQueueHarness(db)` — one scratch schema plus a `Database` per identity (`app`, `maintenance`, `owner`), the schema installed and dropped by the layer itself. `layerWorker(config?, clock?)` — `JobWorker \| Jobs \| Database` composed on the maintenance client, `background: false` by default and `JobClock.layerTest` by default (a case that wants to _be_ a skewed replica passes `JobClock.layerOffset(...)` as the second argument). `asApp` / `asMaintenance` / `asOwner` — run an effect under one identity's `Database`. `readJobs(queue?)` — reads every column of the jobs table as the **owner**, the one identity neither production role may use, which is what lets the suites observe state the application and maintenance roles cannot read back themselves. `DeliveryHarness` / `layerDeliveryHarness(db)` — the above plus a full Studio scratch schema, for handler suites that need both. |

Settable per-call behaviour, so a case can make one send fail or hang while the next succeeds.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

**`background: false`** is `layerWorker`'s default: nothing is forked, so a
suite drives `drainOnce`, `reapExpired`, `deleteExpired`, and `tickSchedules`
directly and deterministically — this is the `JobWorkerInline` mode #1927 §11
describes. `__tests__/notify.test.ts` and one case in `__tests__/metrics.test.ts`
("reads the depths on a fiber of its own") are the deliberate exceptions,
passing `background: true` because real forked fibers and real timing are
what each is proving.

**`TestClock`** drives virtual time through nearly every suite
(`__tests__/queue.test.ts`, `__tests__/cron.test.ts`,
`handlers/__tests__/sign-in-email.test.ts`,
`handlers/__tests__/denied-attempts-summary.test.ts`,
`__tests__/maintenance.test.ts`) because the queue asks `JobClock` — ultimately
the Effect `Clock` — for every timestamp it writes rather than asking the
database's own `now()`, which is the one deliberate divergence from pg-boss
that makes this possible at all.
`handlers/__tests__/denied-attempts-summary.test.ts` (lines 69–78) documents a
sharp edge of that: `TestClock.adjust`/`setTime` replays every
`Effect.sleep` scheduled between the current instant and the target one, in
order, and the connection pool underneath the suite's SQL clients keeps a
repeating sleep running for its own lifetime — so a jump of years never
finishes. That suite bounds every case's step to `CASE_STEP = Duration.minutes(10)`
for exactly this reason, and any future suite that drives `TestClock` a long
way forward against a real Postgres connection should expect the same hang
and bound its jumps the same way.

**`excludeTestServices` for the notify suite.** The `layer(...)` helper from
`@effect/vitest` merges `TestEnv` (which includes `TestClock`) into every
suite by default. `__tests__/notify.test.ts` calls
`layer(layerQueueHarness(db!), { excludeTestServices: true })` to opt out,
because it is the one suite in this directory that has to run in real time:
its claim is a wall-clock budget (`Effect.sleep`, a 500 ms window) that
`LISTEN`/`NOTIFY` beats and plain polling does not, and a virtual-time jump
past the poll interval would make that claim vacuous rather than proving
anything about latency.

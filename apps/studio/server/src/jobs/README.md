# The job queue

This directory is Studio's background-job queue: the five queues
(`invitation-delivery`, `invitation-delivery-dead-letter`, `sign-in-email`,
`protocol-store-gc`, `denied-attempts-summary`), the worker that runs them,
the cron schedules, and the handlers. It replaced pg-boss on 16 Sep 2026
(#1957) and keeps pg-boss's semantics where they mattered — the retry ladder
and its jittered backoff, the singleton policy, dead letters, retention, the
clock-skew warning — see §2 for each, with the ruling behind every
difference. The worker program (`src/programs/worker.ts`) runs it; the web
program (`src/programs/serve.ts`) creates jobs through the same
`Jobs.enqueue`, on the caller's own `Transaction`. The queue's schema is
`studio_jobs`, a schema of its own so that a schema push that reconciles
`public` never touches it.

It exists for two guarantees.

**The transaction guarantee.** `Jobs.enqueue` (`jobs.ts`) requires the
`Transaction` service, and nothing but `TenantScope.open` /
`MaintenanceScope.open` / `MaintenanceScope.openTenant` (`src/db/tenant.ts`)
provides it. Enqueuing issues one
`INSERT INTO <schema>.jobs`, on the caller's own connection: `SqlClient`
routes every statement by the fiber's `TransactionConnection` service, so
there is no second connection an enqueue could reach for even if it wanted
one. A domain row a command writes and the job it schedules therefore commit
together or not at all — this is the reason the queue exists rather than
Studio keeping pg-boss's own two-pool design. `__tests__/transaction.test.ts`
proves it with three oracles, in increasing strength: rollback and commit
symmetry (failing the transaction body leaves zero domain rows and zero job
rows; letting it finish leaves one of each), the invisibility oracle (while
the caller's transaction is still open, a _second_ connection — a different
pool entirely — reads zero job rows; read-committed isolation means this can
only be true if the insert ran on the first connection, which is what "in the
transaction" means), and same-backend-pid (`pg_backend_pid()` read inside the
transaction, immediately after the domain insert and the enqueue, equals the
pid the domain insert ran on, checked against a third connection's different
pid so the equality cannot be an artefact of a single-connection pool). A
fourth proof is at the type level: `jobs.enqueue(...)` outside a transaction
does not compile (`Effect.runSync` demands `R = never`; `enqueue` leaves
`Transaction` in `R`), asserted with a `@ts-expect-error` so the probe cannot
silently rot into a stale comment. `Jobs.layerRecording` — the fake the domain
command suites use instead of a database — keeps the same requirement, so a
command tested under it is held to the same guarantee it ships with.

**Integration with the planned services.** The queue is built directly on the
`Database` / `Transaction` / `Jobs` / `JobWorker` names and shapes #1927 §4
plans for Studio generally, not a vocabulary of its own. Stage 3 has since
made the first two real: the clients live in `src/db/client.ts` and the
transaction and its scopes in `src/db/tenant.ts`, and the queue holds
`MaintenanceDatabase` — the worker runs every statement as the maintenance
role. It already depends on one of stage
1's real services: the mail handlers (`handlers/invitation-delivery.ts`,
`handlers/sign-in-email.ts`) send through `Mailer` (`src/mail/mailer.ts`),
whose `sendTeamInvitation` and `sendMagicLink` fail with `MailFailed` or
`MailNotConfigured`. One other dependency is not Effect yet — the Valkey rate
limiter — and is held behind a seam described in §4 until a later stage moves
it.

## 1. Schema

`schema.ts` renders the DDL and grants as two SQL strings,
`jobSchemaSql(schema)` and `jobSchemaGrantsSql(schema)`, both idempotent
(`CREATE ... IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`/`TRIGGER`) so a
schema application that finds `studio_jobs` already installed reapplies it
rather than refusing or dropping it. `assertSchemaName` checks every
interpolated schema name against `/^[a-z_][a-z0-9_]*$/` and against Postgres's
63-byte identifier limit before it reaches the DDL string. The length check is
not cosmetic: `CREATE SCHEMA` truncates a longer name _silently_, so the
install would look healthy, while `pg_notify` on the same 64-byte channel
raises and `@effect/sql-pg`'s `validateChannelName` refuses the matching
`LISTEN` — which `worker.ts` turns into a dead layer. Every name this build
installs under is well inside it (`studio_jobs` is 11 bytes, a suite's
`studio_test_<12 hex>` 24, the delivery suite's sibling 30).

### `<schema>.jobs`

| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                                             | `uuid` primary key, `gen_random_uuid()`.                                                                                                                                                                                                          |
| `queue`                                                          | The queue name.                                                                                                                                                                                                                                   |
| `payload`                                                        | `jsonb`, decoded against the queue's Effect Schema on both the enqueue and the claim side (`queues.ts`).                                                                                                                                          |
| `state`                                                          | `created \| active \| completed \| failed \| dead`, default `created`. `dead` is reserved for a payload that no longer decodes — no retry can fix it, so it is distinct from an ordinary `failed` row and a dead-letter copy is never made of it. |
| `policy`                                                         | The queue's policy (`standard` or `singleton`), stamped at enqueue. | `attempts`                                                       | Incremented by the claim, not after the handler runs, so a process that dies mid-handler still leaves the attempt spent.                                                                                                                          |
| `singleton_key`                                                  | The per-enqueue `singletonKey`, nullable. | `expire_in_seconds`                                              | The lease length for one claimed attempt, read off the row at claim time so a job keeps the expiry it was enqueued under.                                                                                                                         |

| `last_error`                                                     | The most recent failure message, truncated to 1,000 characters.                                                                                                                                                                                   |
| `outcome`                                                        | What the handler returned: `completed \| suppressed \| uncertain`.                                                                                                                                                                                |
| `dead_letter_of`                                                 | The id of the job this row is a dead-letter copy of, if any.                                                                                                                                                                                      |
| `created_at`, `completed_at`                                     | Self-explanatory.                                                                                                                                                                                                                                 |

### `<schema>.job_schedules`

`name` (primary key), `cron`, `queue`, `payload`, `next_run_at`. One row per
declared cron schedule, upserted by `JobWorker.schedule` so the last replica
to boot with a changed cron expression wins. The upsert recomputes
`next_run_at` only when the cron expression itself changed; a boot that merely
re-registers the same schedule leaves the stored time alone, because
overwriting it would push an occurrence that had already come due forward by
up to a whole interval and skip it.

### Indexes

| Index                       | Predicate                                                                                         | What it is for                                                                                                                                                                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `jobs_claim_idx`            | `(queue, run_at, created_at) WHERE state = 'created'`                                             | The claim's own lookup.                                                                                                                                                                                                                                                        |
| `jobs_expiry_idx`           | `(locked_until) WHERE state = 'active'`                                                           | The expiry reaper's scan.                                                                                                                                                                                                                                                      |
| `jobs_retention_idx`        | `(queue, completed_at) WHERE state IN ('completed','failed','dead')`                              | The retention pass over terminal rows.                                                                                                                                                                                                                                         |
| `jobs_keep_until_idx`       | `(queue, keep_until) WHERE state = 'created'`                                                     | The retention pass over unclaimed rows.                                                                                                                                                                                                                                        |
| `jobs_singleton_idx`        | UNIQUE `(queue, singleton_key) WHERE singleton_key IS NOT NULL AND state IN ('created','active')` | The per-enqueue `singletonKey`: one job per (queue, key) among live states.                                                                                                                                                                                                    |
| `jobs_singleton_active_idx` | UNIQUE `(queue) WHERE state = 'active' AND policy = 'singleton'`                                  | The `singleton` _policy_: at most one active job per queue. The claim's `NOT EXISTS` guard (worker.ts) is the same rule tried first; this index is the belt that makes the rare race — two workers passing the `NOT EXISTS` together — impossible rather than merely unlikely. |

### The notify trigger

`notify_job()` is a `plpgsql` function that runs `PERFORM
pg_notify('<schema>', NEW.queue)`; `jobs_notify_trigger` fires it `AFTER
INSERT OR UPDATE OF state ON <schema>.jobs FOR EACH ROW WHEN (NEW.state =
'created')`. The channel is the schema's own name (`jobNotifyChannel`), so
production's `studio_jobs` and a suite's scratch sibling never wake each
other's workers, and the payload is the queue name, which is all a worker
needs to release the right poll fiber. `pg_notify` is transactional, so
nothing is announced until the writer's transaction commits — which means
_any_ writer that leaves a row `created` (an enqueue, the expiry reaper
putting a job back, a script writing the table directly, an operator's manual
`UPDATE`) wakes a listening worker with no application code having to
remember to announce it. Because the trigger's body is dollar-quoted
`plpgsql`, every installer that applies this schema must split the DDL with
`splitStatements` (`src/db/statements.ts`), not on `;` — a naive split would
cut the function body in half.

### Grants (`jobSchemaGrantsSql`)

| Role                 | May                                                                                                                                                                                                                                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app` (both)         | `USAGE` on the schema; `INSERT` on `jobs`; `SELECT (id)` on `jobs` — nothing else. This is what the request-serving role needs to create a job and read back its id, and no more: the job table is one table for every team, so a role that could read a payload or the `state` column could read every team's queued work. |
| `maintenance` (both) | `USAGE` on the schema; `ALL` on `jobs` and `job_schedules`.                                                                                                                                                                                                                                                                 |
| Both                 | `EXECUTE` on `notify_job()` — a trigger function runs as the role that fired it, so the application needs this to insert at all.                                                                                                                                                                                            |

`dropJobSchemaSql` is `DROP SCHEMA ... CASCADE`, used by the suites to remove
a scratch schema wholesale.

| **LISTEN/NOTIFY with poll fallback** | The worker holds one `sql.listen(channel)` for its process life (`forkListener`), reserving one pooled connection — which is why the pool is sized with a connection to spare. Each queue has a `Latch`, starting **open** so a worker that boots onto a backlog drains it immediately rather than waiting out the first poll interval; the poll loop is `race(latch.await, sleep(pollInterval))` then drain-until-idle, and a `NOTIFY` payload opens the matching queue's latch. Default `pollInterval` is **2 s**. The acquire and the take loop are one unit under `Effect.repeat` on an exponential backoff from 200 ms capped at **30 s**, each attempt in its own scope: a lost reserved connection fails every listen queue with `Cause.interrupt()`, so the take loop simply ends, and without the retry the worker would be deaf for the rest of the process's life with no log line. The ladder is computed from the number of losses since the last successful acquire rather than from the schedule's own recurrence count, so it resets when the listener comes back. The first loss of a run logs a warning carrying the cause, every consecutive loss after it a debug line, and the acquire that ends the run an info line naming how many there were — so a listener that cannot be re-acquired at all says so once and then goes quiet, where capping at the poll interval and warning every time wrote some forty thousand lines a day. What is watched instead of log volume is `JobWorker.listening`, which `jobsCheck` reports as `degraded`. The layer's scope closing skips the failure continuation, so a stop ends the loop rather than reconnecting through it. Proven in `__tests__/listener.test.ts`, which terminates the listener's backend from another connection and shows both halves: a job enqueued afterwards still settles inside the 500 ms budget with the poll interval an hour away, and the readiness probe reads `degraded` in the window before the reconnection and `ok` after it. | pg-boss's poll floor is 0.5 s, with no notify mechanism.                                                                                                                                                                                                                                                     | With the trigger in place, polling is now the safety net (a dropped listener connection, a row made `created` while the listener is reconnecting) rather than the primary path, so 2 s rather than pg-boss's 0.5 s floor. | **`JobClock` skew correction**       | `clock.ts`. A `Context.Reference` — not a `Context.Service` — whose default is `{ now: DateTime.now }`, the uncorrected Effect `Clock`. | **Outcomes and logging**             | A handler returns one of `completed \| suppressed \| uncertain` (`JobOutcome`, `worker.ts`); it never says `retrying` or `failed` — `drainOnce` derives those from the row's own attempt counters after the handler's `Effect` fails: a step that still has retries left is logged with `Effect.logWarning` ("job ... retrying after attempt ..."), one that has none left with `Effect.logError` ("job ... failed on attempt ..."). A `completed` or `suppressed` settle logs at debug — the queue working — but an `uncertain` one logs at `Effect.logWarning`: nothing sets a minimum log level, so Effect's default of `Info` drops a debug line entirely, and `uncertain` ("a side effect left the process and its record could not be written") is the one outcome nothing will retry and a person has to look at. A payload that fails to decode against the queue's schema (`JobPayloadUndecodable`) settles the row to `dead` and logs an error — no ladder applies, since no retry could fix a payload the schema itself rejects.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | pg-boss has no equivalent three-way outcome; success is the absence of a throw.                                                                                                                                                                                                                              | Per #1927 §11.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Graceful stop**                    | `forkBackground`'s finalizer (registered _after_ every recurring fiber is forked, so scope finalizers — which run in reverse — execute it _before_ those fibers are interrupted) sets `fetching = false`, then waits up to `stopTimeout` (default 25 s) for in-flight handlers to drain via the worker's semaphore; if the window elapses it logs a warning and lets the scope interrupt whatever handlers remain. The whole claim-run-settle step in `drainOnce` — not just the handler — holds a semaphore permit, so a stop cannot interrupt a fiber between a handler finishing and its outcome being written. `drainOnce` re-reads `fetching` **inside** that permit, before its claim: a poll fiber that passed its own check and then waited for a permit would otherwise claim during the stop window, spending an attempt on a job the scope is about to interrupt and leaving the row `active` until its lease expired. One of that last handler's dependencies is not Effect yet; it is a
`Context.Service` seam with a live layer wrapping today's Promise
implementation and a test layer beside it, so the handler itself never sees a
`Promise`:

- **`DeniedAttemptsStore`** (`handlers/denied-attempts/store.ts`) wraps
  today's `RateLimitStore` (`src/rate-limit/store.ts`, ioredis). The live
  layer (`DeniedAttemptsStore.layer(store)`) wraps the exact calls the handler
  needs — a cursor `SCAN`, the claim's Lua (`CLAIM_SCRIPT`: rename a live
  window onto its claim key, or extend an existing claim once it has gone
  stale), `discardClaim`, and the scope-count drain (`DRAIN_SCRIPT`) — each in
  `Effect.tryPromise`. `DeniedAttemptsStore.layerAbsent` is what stage 3 wires
  when `REDIS_URL` is unset: `configured: false`, every operation a no-op,
  which is the same posture today's optional `deps.store` takes. A later
  stage (#1927's stage 4) replaces this seam by turning `RateLimitStore`
  itself into an Effect service.
  There is no writer seam any more. `appendDeniedAuditSummary`
  (`src/audit/denial-summary.ts`) is an ordinary Effect on
  `MaintenanceDatabase`: it opens `MaintenanceScope.openTenant`, takes the team
  advisory lock, reads the team label under `FOR UPDATE` and appends through
  `audit/store.ts` — the same three the request plane's `audited` uses, so a
  summary row is labelled and sequenced exactly like every other event in the
  log. It is not `audited` itself and cannot be: that combinator opens a
  `TenantScope` on the _application_ client and stamps the actor from the
  request's `Principal`, and a summary has neither.

**The two-pool hazard is gone with the seam.** The writer tag existed to carry
the worker's maintenance `pg.Pool` across the Effect boundary, and its own
documentation named the cost: the row was written through that pool while the
handler's `summaryAlreadyWritten` read `audit_events` through the queue's
`Database`, so two clients pointed at different databases, roles or search
paths would report every already-written summary as missing and write a second
copy of an immutable event. Both now run on the one `MaintenanceDatabase`.

`handlers/denied-attempts/testing.ts` holds the store seam's test doubles
beside the seam itself rather than inside a suite: `layerMemoryStore` (a `Map`
honouring the claim script's rename/stale-retake semantics exactly, plus
`DeniedAttemptsMemory` for seeding and inspecting it and forcing one operation
to fail).

## 5. Installing the schema

`install.ts` provides the schema in both shapes a caller needs, sharing one
statement list (`jobSchemaStatements`) so the bytes installed by a
deployment and by a suite's scratch schema cannot drift:

- **`installJobSchema(db: pg.PoolClient, schema: string)`** — the
  node-postgres path, applying `splitStatements(jobSchemaSql(schema))` then
  `splitStatements(jobSchemaGrantsSql(schema))` one statement at a time.
  `splitStatements` (`src/db/statements.ts`) is dollar-quote-aware; a naive
  split on `;` would cut the trigger function's `plpgsql` body in half. Must
  be called inside an existing transaction — a failure part-way would
  otherwise leave a schema with only some of its tables. The DDL's `IF NOT EXISTS` / `OR REPLACE` idempotence is
  what makes this safe to call on every schema application.
- **`installJobSchemaEffect(schema: string)`** — the same statement list
  over an open `Transaction` (not the client, for the same reason
  `Jobs.enqueue` takes `Transaction`: the requirement is what says this runs
  inside a transaction someone else opened), for a worker that owns a client
  and creates the schema through a scope.

There is no version stamp of the queue's own: the DDL strings feed into
Studio's overall `SCHEMA_FINGERPRINT`, so a change to either function is a
stale database like any other, caught by the same fingerprint check every
other sidecar goes through.

The suites' own harness (`__tests__/support.ts`) reuses the exact same
statements. `layerQueueHarness` builds a scratch schema named
`studio_test_<uuid>` per suite, applies `jobSchemaSql` +
`jobSchemaGrantsSql` through the owner identity inside a transaction, and
drops it via `dropJobSchemaSql` in a layer finalizer.
`layerDeliveryHarness` — for suites whose handlers read both Studio's own
tables and the job queue — is built on `TestDatabaseLive`
(`src/__tests__/support/database.ts`), which provisions a full Studio scratch
schema and installs the queue into a `<studioSchema>_ejobs` sibling schema with
the same statements, named so the `studio_test_%` sweep in `scripts/apply.ts`
reclaims it after a crashed run. It exposes that harness's three clients as
the queue harness's, and provides `TestDatabase` beside it for the suites'
fixtures and oracles.

## 6. How the programs wire it

Two programs use this directory, and they use different halves of it.

**The web process** (`src/programs/serve.ts`) only creates jobs, through the
same `Jobs.enqueue` the worker uses. It composes `Database.layerFromEnvironment`
(the application role — the role that may create a job and can do nothing else
with it), `JobClock.layerApplication()`, `Jobs.layer({ schema: JOB_SCHEMA })`
and `AuditSignal.layer`, captures the lot as one `Context`, and hands it to the
two promise-shaped consumers that cannot take layers: the protocol builder's
oRPC router and better-auth's sign-in mail callback (`rpc/deps.ts`). Every
`/rpc` command takes them from its own environment.

Until stage 3 the web process enqueued through a node-postgres twin
(`src/jobs/client.ts`) that rendered the same `insertJobStatement` on the
caller's `pg.PoolClient`. It is deleted. The one thing it did differently was
"now": it passed `null`, which the statement renders as the database's own
`now()`, because the web process had no `JobClock`. `Jobs.enqueue` passes an
instant as a parameter — which is what makes the whole queue `TestClock`-
drivable — so the web process is given `JobClock.layerApplication()`, the same
measurement, interval and warning threshold as the worker's, on the
application client instead of the maintenance one. Without it a replica whose
clock ran fast would enqueue jobs into the future for an unskewed worker to
leave sitting there.

There is still nothing to start and nothing to stop for the enqueue itself,
and the boot checks wait only for the schema gate and the keyring — a statement
against a database that has not been migrated yet fails the one request that
made it, which is what the development lane needs, where `pnpm dev` can finish
applying the schema long after the process booted.

**The worker process** (`src/programs/worker.ts`) runs the queue. Over
`Environment` it composes `DatabasePool.layerMaintenance(db)` — the `pg.Pool`
the secrets check still needs — and then, in acquisition order:

1. `Health`: the loopback readiness listener. First, so a `docker compose up`
   reads an honest `failing` naming the schema rather than a refused
   connection. Its `jobs` entry is `jobsCheck(worker, database)` reached
   through a `Ref` the graph fills in, which answers `failed: not started`
   until the queue's own layers exist — they are built after the gate below,
   and a check cannot hold a service that has not been made yet.
2. `SchemaStatus.layer`, then `SecretsVerified`: the schema gate and the
   keyring check (#1900). Everything the queue does is after both — nothing
   may claim a job against a schema this build did not make, or sign a webhook
   delivery with a keyring that cannot produce the key ids already stored.
3. `MailerLive`, then `MaintenanceDatabase.layer({ url, applicationName:
'studio-worker' })` — the client the queue runs on, and the only one of
   `src/db/client.ts`'s three the worker builds. Every read and every write
   the queue and its handlers make goes through this one client, including the
   denied-attempts summary's audit append — which is why §4 no longer has two
   clients to keep in step.
4. `JobClock.layer()` (the production skew correction, not the test clocks),
   `Jobs.layer({ schema: JOB_SCHEMA })`, then
   `JobWorker.layer({ schema: JOB_SCHEMA })` — `background: true` and
   `listen: true` by default, so the poll fibers, the reaper, the retention
   pass, the cron tick and the `LISTEN` are all forked here. Its scope
   finalizer is the graceful drain: 25 seconds, and because `Health` was
   acquired first it closes last, so `/readyz` stays answerable throughout.
5. `DeniedAttemptsStore` — the live store where `REDIS_URL` is set,
   `layerAbsent` otherwise — then `JobHandlersLive` (§3), which registers the
   handlers and writes the schedules.
6. `JobQueueMetrics.layer()` for `studio_jobs_queue_depth` and the backlog
   warning. Readiness does not depend on it: the worker's own poll fibers set
   `ready` from their first answered claim.
7. `JobMaintenanceGate.layer()` over `MaintenanceState.layerMaintenance`: the
   `deployment_state` flag `studio-api maintenance on|off` writes, read on this
   process's maintenance client.
8. `Started`: the handle the readiness check reads, and the boot line.

(the worker told `listen: false`, whose verdict is about a listener it never
forked) are the deliberate exceptions, passing `background: true` because real
forked fibers and real timing are what each is proving. `layerNotifiedWorker`
in `__tests__/support.ts` is the shape the two listener suites want of it: a
forked worker whose poll interval is an hour, so only a notification can
explain a prompt drain.

**`TestClock`** drives virtual time through nearly every suite
(`__tests__/queue.test.ts`, `__tests__/cron.test.ts`,
`handlers/__tests__/sign-in-email.test.ts`,
`handlers/__tests__/denied-attempts-summary.test.ts`,
`__tests__/maintenance.test.ts`) because the queue asks `JobClock` — ultimately
the Effect `Clock` — for every timestamp it writes rather than asking the
database's own `now()`, which is the one deliberate divergence from pg-boss
that makes this possible at all.
`handlers/__tests__/denied-attempts-summary.test.ts`'s `CASE_STEP` documents a
sharp edge of that: `TestClock.adjust`/`setTime` replays every
`Effect.sleep` scheduled between the current instant and the target one, in
order, and the connection pool underneath the suite's SQL clients keeps a
repeating sleep running for its own lifetime — so a jump of years never
finishes. That suite bounds every case's step to `CASE_STEP = Duration.minutes(10)`
for exactly this reason, and any future suite that drives `TestClock` a long
way forward against a real Postgres connection should expect the same hang
and bound its jumps the same way.

**`excludeTestServices` for the wall-clock suites.** The `layer(...)` helper
from `@effect/vitest` merges `TestEnv` (which includes `TestClock`) into every
suite by default. `__tests__/notify.test.ts`, `__tests__/listener.test.ts`,
`__tests__/concurrency.test.ts` and `settle.test.ts`'s "claiming during a
graceful stop" call
`layer(layerQueueHarness(db!), { excludeTestServices: true })` to opt out,
because each has to run in real time. The two listener suites' claim is a
wall-clock budget (`Effect.sleep`, the 500 ms `NOTIFY_BUDGET` they share) that
`LISTEN`/`NOTIFY` beats and plain polling does not, and a virtual-time jump
past the poll interval would make that claim vacuous rather than proving
anything about latency. The stop window is a poll fiber and a finalizer racing
for one semaphore permit, which `TestClock` would decide by fiat.

**`__tests__/concurrency.test.ts` is where two claims overlap.** Every other
suite here drives `drainOnce` sequentially in one fiber, which is what buys
them virtual time — and is also what leaves `FOR UPDATE SKIP LOCKED`, the
singleton `NOT EXISTS` guard and the `23505` a losing claim swallows with no
oracle at all, because nothing is ever contended. This suite supplies the
contention two ways. A raw `pg` connection opened beside the harness's own
pools (they share nothing with it, which is the point) holds a row lock or an
uncommitted `active` row while the worker claims against it: one case proves
the claim steps over a held row inside a two-second budget rather than waiting
on it, and one proves that a claim which loses the singleton index's race
answers `idle` with its job still `created` and its attempt unspent. That
second case waits on `pg_blocking_pids` rather than on a sleep — committing
the holder before the claim is actually blocked would let the `NOT EXISTS`
guard answer first and the case would pass without the index ever raising.
Two further cases run two real background workers over one schema: twenty jobs
handled exactly once between them, and five jobs on a singleton queue whose
handler intervals never overlap. The two workers are provided with
`Effect.provide(layerWorker(...), { local: true })` and a freshly built layer
each — a layer is otherwise shared between `provide` calls, so nesting one
twice hands both scopes the _same_ worker, whose second `work()` overwrites
the first's registry entry and leaves the case measuring one worker while
claiming to measure two.

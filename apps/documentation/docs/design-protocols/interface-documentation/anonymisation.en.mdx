<InterfaceMeta type="Utility" creates="A passkey that can be used to anonymize user data" usesprompts="false">

</InterfaceMeta>

</InterfaceSummary>

This interface lets participant data be encrypted on-device, in such a way as to prevent anyone other than the participant, including the researcher, from accessing it.

Adding this interface to your protocol will enable you to select which node attributes are encrypted. When viewing this stage, your participants will be asked to choose a passphrase, and to enter it a second time to confirm it. The passphrase is what protects their data. Every attribute you mark as encrypted is encrypted during interviews.

In the **Encrypted attributes** section of the stage editor, each node type in your protocol has its own switch. Turn a type's switch on, then tick the text attributes of that type that should be encrypted. Only text attributes can be encrypted, and edge attributes are not offered. Turning a type's switch off stops encrypting every attribute of that type at once; Architect asks you to confirm before it clears them.

### Passphrase length

By default, a participant must choose a passphrase of at least 8 characters.

To set your own limits, use the **Passphrase validation** section of the stage editor. Switch on **Minimum text length** to set the shortest passphrase you will allow, and **Maximum text length** to set the longest. A minimum you set always replaces the default of 8, even if yours is shorter.

Length rules apply when a participant first chooses their passphrase, which is also when they confirm it by entering it a second time. When they come back to the interview later, they only need to enter the same passphrase again.

### How answers are protected

Protection happens on the participant's own device, using the [Web Crypto API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API). Answers are encrypted before they are stored, so the interview data never holds them in readable form.

- **One key for each interview.** When a participant chooses a passphrase, the interview derives a single encryption key from it. The key is derived with PBKDF2-SHA256, using 600,000 iterations and a random salt that is created for that interview. This is deliberately slow, which makes guessing a passphrase expensive.
- **Strong encryption for every answer.** Each encrypted answer is encrypted with that key using AES-256-GCM, with a fresh random value for every answer.
- **Answers are tied to their place.** Each answer is bound to the person and the question it belongs to, so an encrypted answer that is copied to another person or question cannot be read.
- **Answers are padded.** Each answer is padded to a fixed block size before it is encrypted, so the length of an encrypted answer reveals less about what it says.
- **The passphrase is checked, not stored.** The interview saves a small check value, encrypted under the key. When a participant enters their passphrase again, the interview uses the check value to confirm that it is the one they chose, without ever storing the passphrase itself.

The passphrase is never stored. The key is held only in memory, in the browser or app running the interview, and is never saved. This means that refreshing the page, closing the tab, or visiting the interview from another browser or device will require the participant to enter their passphrase again. The encrypted answers are stored with the rest of the interview, and can only be read by someone who knows the passphrase.

### If a participant forgets their passphrase

<TipBox danger>

A forgotten passphrase cannot be recovered by anyone, including you, the participant, and the Network Canvas team. The answers it protects stay unreadable.

</TipBox>

Make sure participants understand this before they choose a passphrase. The **Task explanation** section of the stage editor is the place to tell them. A longer passphrase is harder to guess, but also harder to remember.

### Exporting protected answers

When exporting this data, the encrypted attributes will not be included in the export file in readable form. Every value is replaced with the string `ENCRYPTED`.

### Answers protected by the experimental version

In schema 8 protocols, the Anonymisation interface was an experimental feature, and it protected answers in an earlier format. Answers protected that way cannot be read after you upgrade to schema 9, even with the right passphrase. After the upgrade:

- Interviews that contain these answers still open.
- The earlier protected answers appear as "Answer unavailable" where the interview would have shown them. They are still exported as `ENCRYPTED`.
- New answers are protected in the way described on this page, once the participant chooses a new passphrase.

If you have interviews in progress that use the experimental version, consider finishing them before you upgrade the app. See [Schema version 9](/en/get-started/protocol-schema-information#schema-version-9) for what else changes when you migrate a protocol.

### Best Practices

<GoodPractice>

Ensure that the passphrase is strong and unique to prevent unauthorized access to the encrypted data, but balance this against the need for participants to remember it easily.

</GoodPractice>

<GoodPractice>

Use this feature to encourage disclosure of sensitive information, such as names, in a way that makes participants feel secure about their privacy. This can lead to more honest and complete responses in interviews.

</GoodPractice>

<GoodPractice>

When using the anonymisation interface, clearly communicate to participants how their data will be used and the importance of the passphrase for accessing their encrypted data, including that a forgotten passphrase cannot be recovered. This transparency builds trust and encourages participation.

</GoodPractice>

### Try to Avoid

<BadPractice>

Do not use the anonymisation interface for data that is not sensitive or does not require encryption. This interface is intended for use with sensitive data where privacy and security are paramount.

</BadPractice>

<Definition>
  Piped text is text that changes value dynamically based on interview data or
  context. When you design your interview, it allows you to include a
  placeholder that is replaced by the real dynamic value when the participant
  sees the text.
</Definition>

## Purpose

Computer-assisted survey instruments have long tailored question wording to the respondent by inserting earlier answers into later questions, a technique usually called _piping_ or _text fill_. Network instruments have a particular need for it. A name interpreter asks the same questions about each alter in turn, and a Dyad Census asks the same question about every pair of alters. Without piping, such questions must refer to the alter indirectly ("this person", "these two people") and rely on the participant to connect the question with the node on the screen.

Naming the node in the question removes that inferential step. "Did you visit Northwestern University or study there?" identifies its referent unambiguously, while "Did you visit this university, or study there?" does so only in combination with the visual layout of the interface. The difference is greatest when nodes resemble one another, when the participant has named many alters, and when the interview is administered by an interviewer who reads the question aloud.

Piped text also allows a later question to build on an earlier one. A question can recall the date that the participant gave for a life event, address the participant by the name that they provided, or be phrased differently according to how the participant answered a previous question. Text can also contain [logic](#logic), which chooses between alternative versions according to an earlier answer or to rules about the participant, a node or an edge.

Network Canvas fills piped text from data already recorded in the interview. Inserting a value into a question does not store that value a second time, and does not send it anywhere else.

<TipBox>

Piped text requires [schema 9](/en/get-started/protocol-schema-information#schema-version-9). Protocols that use it are built in Architect and run in Fresco 5.0 or later, or Interviewer 9.0 or later.

</TipBox>

## Methodological considerations

Piping changes the stimulus that each participant receives. Two participants answering the "same" name interpreter question read different words, because each question names a different alter. For most network instruments this is the intended effect: the construct being measured is the participant's relationship with a specific alter, and naming that alter makes the question more precise. It nevertheless calls for three precautions.

- **Report the template, not the realized wording.** When describing an instrument in a publication or an ethics application, give the question as written in the protocol, with the piped element marked, and state which attribute supplied it. Where a translatable string contains [logic](#logic), report each of its wordings, together with the rules or the answer that selects it.
- **Check the wording for when information is missing.** Any attribute can be absent when a question is shown, and a missing value shows nothing (see [When information is missing](#when-information-is-missing)). Where the text would then read poorly, give it another version for that case. That version is part of the instrument and should be reviewed with the same care as the primary wording.
- **Pilot with realistic data.** Long names, names that are also common words, and unexpected answers can produce questions that read poorly. Cognitive interviews and pilot sessions (see [Piloting Your Study](/en/get-started/planning-a-study/piloting-your-study)) should include the range of values that participants are likely to provide.

Piping is also a design decision about disclosure. A question that repeats a participant's answer displays that answer on screen again, which may matter when interviews take place in shared or public settings. [Encrypted attributes](/en/design-protocols/key-concepts/variables#encrypted-variables) are never offered for piping.

## What can be piped

Each piece of information inserted into a translatable string is a _piped value_. A piped value is one of the following:

- **Today's date.** This is the only information about the interview itself that a translatable string can show. It is the date on which the participant reads the string.
- **An attribute of the participant**, such as a name or an answer from an Ego Form.
- **The label of a node that the string concerns**, on stages and forms that ask about one node or two nodes at a time. This is the text that the interview displays on the node, so a question on a Dyad Census can ask "Are Jim and Alice friends?" using the same names that the participant sees on the two nodes. See [Node labels](#node-labels).
- **An attribute of the node or edge that the string concerns**, on the same stages and forms. A Per Alter Form question can, for example, name the university that the participant nominated for that node on an earlier stage.

The following kinds of attribute can be piped: text, number, scalar, date, boolean (yes or no), ordinal and categorical. Encrypted attributes are never offered, and neither are layout or location attributes.

The values available to a translatable string depend on where the string appears. See [Where piped text can be used](#where-piped-text-can-be-used).

By means of logic, a translatable string can also change its wording without showing a value. See [Logic](#logic).

## Inserting piped text in Architect

Every text field that accepts piped text has an **Attribute** button in its toolbar. To insert a value:

1. Place the cursor in the text where the value should appear.
2. Click **Attribute**, or type `{`.
3. A list shows the values that this string can show. Type to filter the list.
4. Choose a value by clicking it, or press Enter to choose the highlighted value.

![The Attribute list open in the question of a Per Alter Form field. Node label is listed first under Node attributes.](/assets/img/piped-text/insert-menu.png 'Inserting a piped value into a form field question')

The list groups values under these headings, in this order:

- **Node attributes**: the label and attributes of the node that the translatable string refers to, that is, the node that a form or a prompt asks about. A node's label is listed as **Node label**. Where the string refers to an edge, the edge's attributes are listed under **Edge attributes**. Where the string refers to two nodes, as with a pair on a Dyad Census or Tie-Strength Census or the two nodes that an edge joins, their values are listed under **First node attributes** and **Second node attributes**, and each value names the node that it belongs to, such as **First node: label**, **First node: nickname** and **Second node: label** (see [Where piped text can be used](#where-piped-text-can-be-used)).
- **Ego attributes**: the participant's attributes.
- **Dynamic attributes**: the stage's [dynamic attributes](#dynamic-attributes), followed by **Create dynamic attribute**.
- **Interview attributes**: today's date.

A value that cannot be used is listed but cannot be chosen, and the reason is shown beneath it. For example, a Boolean attribute whose answers have no labels cannot be shown, because the string would have no words to show for its answer. Its entry reads **Add labels for its yes and no answers first**, or, for an attribute answered with a Toggle, **A Toggle has no labels for its answers. Use a dynamic attribute instead.** See [Different wording for each answer](#different-wording-for-each-answer).

To type a literal brace, press Escape after typing `{`. The list closes and the brace remains in the text.

In the editor, a piped value appears as a pill that carries the name of its attribute, such as **nickname**, in the color of the attribute's type. Where the translatable string concerns two nodes, the pill also names the node, such as **First node: nickname**. A node's label appears as **Node label**, or as **First node: label** and **Second node: label**, and today's date appears as **Today's date**. A pill sits on the line of text like a word, so it does not change the height of the line. The same pills appear in the [translation table](/en/design-protocols/tutorials/translating-your-protocol#the-translation-table) and on the protocol's **Summary** tab.

![A Per Alter Form field whose question reads "Did you visit [Node label] or study there?".](/assets/img/piped-text/value-in-question.png 'A node label piped into a Per Alter Form question')

![A Dyad Census prompt reading "To the best of your knowledge, do [First node: label] and [Second node: label] spend time together outside of class?"](/assets/img/piped-text/pair-prompt.png 'Both nodes of a pair named in a Dyad Census prompt')

An attribute that a stage's translatable string shows, or whose answers determine the wording of that string, counts as in use in the [codebook](/en/design-protocols/key-concepts/codebook). It cannot be deleted until it is removed from that string.

## When information is missing

Any attribute may be missing when the participant reaches a translatable string that pipes it. The participant may have declined to answer, [skip logic](/en/design-protocols/key-concepts/skip-logic) may have bypassed the stage that collects it, or a roster may not include it. Returning to an earlier stage to change an answer, or deleting a node, can also leave an attribute unset, even when the protocol normally collects it beforehand.

A missing value shows nothing: the participant sees the rest of the text without it. Write the text so that it still reads well when the value is missing, or give it another version for that case:

- In a translatable string of several lines, such as the text of an Information stage or a form, put the passage in a [logic block](#logic-blocks) with a rule that the attribute **exists**. Show the value in the version for when the rule is met, and write the **Otherwise** version without it.
- A [dynamic attribute](#dynamic-attributes) or a logic block that has a version for each answer of a categorical, ordinal or Boolean attribute also has an **If not known** version, which is used when there is no answer.

For example, the heading of an Information stage could thank the participant by name. A logic block with the rule that the participant's **first_name** attribute **exists** contains two versions of the heading:

| Version               | Text written                     | Participant sees |
| --------------------- | -------------------------------- | ---------------- |
| If: first_name exists | "Thank you, " **first_name** "!" | Thank you, Sam!  |
| Otherwise             | Thank you!                       | Thank you!       |

Zero and "no" are answers, not missing values: a number equal to 0 is shown as 0, and a yes-or-no answer of no is shown by the label of the no answer. A text answer that is empty or contains only spaces, and a categorical answer with no options selected, count as missing.

Today's date and a node's label are never missing. The one exception is the prompt of an Ordinal Bin or Categorical Bin set to **Tap to place**: once every node has been placed, no node is being placed, so the label of the node being placed shows nothing.

## Node labels

A node's label is not a single attribute. The interview derives it for each node from that node's own data: an attribute named "name"; otherwise one whose name contains "name"; otherwise, for imported data, a column whose name contains "name" even if the codebook does not list it; otherwise the first text attribute that has a value. A node with none of these is shown as "Unnamed" during the interview. The piped label follows the same rules, so it always matches the text displayed on the node, even when two nodes of the same type draw their labels from different attributes. When the label comes from an encrypted attribute, the translatable string shows it in the same way as the node shows it. See [Node Labeling](/en/design-protocols/key-concepts/node-labelling) for more on how labels are chosen.

A Family Pedigree stage labels its nodes in its own way, and its form's questions and hints show the label that the family tree shows: the name that the participant entered, "You" for the participant, or, for a relative left unnamed, the term that the stage assigns according to the relationship, such as "Mother" or "Sister 2". This term comes from the stage's wording and from the kinship words that are chosen in the stage's **Words for family members** setting. As the participant changes a relative's name, gender identity or sex assigned at birth in the side panel, the label shows what the family tree will show after the changes are saved. For an unnamed relative, it is the label that the stage saves as the relative's name when the participant leaves the stage.

The label is the usual way to identify a node in a question, as in "Are Jim and Alice friends?". A specific attribute is preferable when the translatable string needs that particular answer, such as a nickname, even where the label shows something else.

## Logic

Logic gives text alternative versions, of which the participant sees one. Architect offers it in two forms:

- A **[dynamic attribute](#dynamic-attributes)** is a word or phrase inside a sentence that reads differently in different cases, such as "his", "her" or "their". It can be used in any translatable string that accepts piped text.
- A **[logic block](#logic-blocks)** is a section that shows different content in different cases, in a translatable string of several lines, such as the text of an Information stage or of a form. Its versions can contain paragraphs, headings, lists, images and, in a form, fields.

Both choose a version in the same ways, which Architect calls their **Logic** (see [Logic options](#logic-options)), and both use the same [rules](#rules). The participant never sees the logic itself, only the version that applies.

The same kinds of logic can be used in the label that a node type gives its nodes. See [Dynamic labels](/en/design-protocols/key-concepts/node-labelling#dynamic-labels).

### Dynamic attributes

A dynamic attribute belongs to its stage, so it can be used in any translatable string of that stage, as many times as needed. To create one:

1. Place the cursor where the word or phrase should appear.
2. Click **Attribute**, or type `{`, and choose **Create dynamic attribute** under **Dynamic attributes**.
3. In the **Create a dynamic attribute** dialog, choose its **Logic** (see [Logic options](#logic-options)).
4. Set the rules for each case, or choose the attribute whose answer or number decides which version is shown.
5. Write each version. Keep each version short, because it is shown in place of the pill, inside the sentence.
6. Choose **Create dynamic attribute**.

The dynamic attribute is placed in the text as a pill that shows its versions, such as **their / her / his**. It is listed under **Dynamic attributes** in the **Attribute** list of every translatable string of the stage, so it can be inserted in other places too.

Select the pill to open the dynamic attribute's settings, which contain the same controls as the dialog. A change applies everywhere that the dynamic attribute is used on the stage, and the settings say how many places that is. **Remove from this wording** removes the pill from the translatable string that you are editing. Any other translatable string that uses the dynamic attribute keeps it. When the stage is saved, a dynamic attribute that no translatable string uses is removed.

The versions of a dynamic attribute are plain words: they cannot be formatted, and they cannot show values. A version can be left empty, and then nothing is shown in place of the pill. In the editor, an empty version reads **Shows nothing**, and so does the pill of a dynamic attribute whose versions are all empty.

For example, a Per Alter Form question could ask "Where does this person [study / work]?", with a dynamic attribute whose logic is **If … else**:

| Version                 | Wording |
| ----------------------- | ------- |
| If: age is less than 18 | study   |
| Otherwise               | work    |

### Logic blocks

A logic block can be added to any translatable string of several lines that accepts piped text: an Information stage's text, an Anonymisation stage's explanation, a Finish Screen's closing and finished text, and the text of a form. In a form, its versions can also contain fields (see [Showing fields only in some cases](/en/design-protocols/key-concepts/forms#showing-fields-only-in-some-cases)). To add one:

1. Place the cursor where the content should appear.
2. Choose **Logic block** in the editor's toolbar.
3. The logic block is added, and its settings open. Choose its **Logic**, then set its rules or choose its attribute.
4. Write the content of each version in the block.

The block shows its versions one below another. Each version has a label that says when it is shown, such as **If:** followed by its rules, **Otherwise**, the label of an answer, **If not known** or **Any other answer**. A version that has no content reads **Nothing is shown.** In that case, the participant sees nothing.

To change a logic block, choose its settings button. The settings contain the **Logic** control, the rules or the attribute, and **Delete logic block**, which deletes the block with all of its content. When a change to the logic would remove versions that have content, Architect asks before deleting them. In a form, the settings also say that when the participant submits the form, the answers to any fields in versions that are not shown are cleared.

A logic block can be dragged to another place by its handle, and its versions can contain further logic blocks. A logic block cannot be placed inside a list or a paragraph. To change a word or phrase inside a sentence, use a dynamic attribute.

### Logic options

The **Logic** control offers these options. An option that cannot be used in a string is dimmed, and the reason is shown beneath it.

- **If … else** shows one version when rules that you set are met, and another version otherwise. **If not … else** shows the first version when the rules are not met. See [Versions chosen by rules](#versions-chosen-by-rules).
- **Different wording for each answer** gives a dynamic attribute a version for each answer to a categorical, ordinal or Boolean attribute. For a logic block, the same option is called **Different content for each answer**. See [Different wording for each answer](#different-wording-for-each-answer).
- **Wording for singular or plural numbers** gives a dynamic attribute a version for each number form that the language distinguishes, such as "1 child" and "3 children". For a logic block, the same option is called **Content for singular or plural numbers**. See [Wording for singular or plural numbers](#wording-for-singular-or-plural-numbers).
- **Participant or someone else** gives one version for the participant and another version for everyone else. It can be used only in the form of a Family Pedigree stage. See [Wording for the participant or someone else](#wording-for-the-participant-or-someone-else).

### Versions chosen by rules

With **If … else**, the first version is labeled **If:** followed by its rules. With **If not … else**, it is labeled **If not:** followed by its rules. The last version, **Otherwise**, is shown when no other version applies.

The rules are set in the settings of the dynamic attribute or logic block, under **Rules for “If”** (see [Rules](#rules)). **Add else if** adds another version with rules of its own, labeled **Else if:** followed by those rules. The interview tests the versions from the top, and shows the first version whose rules apply. **Remove this case** removes a version together with its rules.

The interview tests the rules again whenever the answers or edges that they test are changed, so the version that is shown stays up to date throughout the interview.

### Rules

Rules are set in the same rule builder that [filters and skip logic](/en/design-protocols/key-concepts/skip-logic) use. What a rule can test depends on what the translatable string refers to:

- **An attribute of the participant.** This is available in every translatable string that accepts piped values.
- **An attribute of the node** that the string concerns, in a string that refers to a node.
- **The edges of that node**: whether the node has an edge of a given type, an attribute of one of its edges, or the number of edges that it has, of one type or of any type. The number can be compared with a number that you give, or with the other nodes of the same type, using **Is the highest among nodes of its type** and **Is the lowest among nodes of its type**. Nodes that tie for the highest, or for the lowest, all match. No node matches when every node of the type has the same number of edges.
- **An attribute of the edge** that a form asks about, in a Per Alter Edge Form's text, questions and hints.
- **An answer on the same form**, in the text, questions and hints of a form. A rule about an answer on the form is tested as the participant answers. In the settings of a logic block, the attribute lists of its rules, and its **Attribute** control, first show the attributes that the form's own fields collect, under **Answers on this form**, and then the other attributes, under **Answers from earlier stages**. An attribute that only a field inside the logic block collects is listed but cannot be chosen, because that field is shown only when the logic block shows it. The reason beneath it reads **A field inside this logic block collects this attribute, so it cannot decide which content the block shows.** The same applies when this logic block is inside one version of an outer logic block, and an attribute is collected only by fields in a different version of the outer logic block. The participant sees only one version of each logic block, so those fields are never shown together with this logic block. The reason beneath it reads **This attribute is collected only by fields in another version of a logic block that contains this block, so those fields are never shown with this logic block.**

A translatable string that refers to no node or edge, such as an Information stage's text or a Name Generator's prompt, can use only rules about the participant. See [Where piped text can be used](#where-piped-text-can-be-used) for what each string refers to.

Where the translatable string refers to two nodes, as with a pair on a Dyad Census, the rules have a **Check rules against** setting, which offers **The first node of the pair** and **The second node of the pair**. Node rules and edge rules are checked against the node that is chosen in that setting.

When there is more than one rule, **Match** sets whether **All rules must match** or **Any rule can match**.

The rules belong to the stage, or to the node type in a dynamic label, and are not part of the translatable string. They are therefore the same in every language of the protocol.

## Different wording for each answer

This logic gives a version for each answer to a categorical, ordinal or Boolean attribute, instead of showing the answer itself. This allows a question to adapt its framing to an earlier response. Choose the attribute in the **Attribute** control. The versions are:

- **If not known**, used when there is no answer.
- One version for each of the attribute's options, named after the option's label. A Boolean attribute without labels of its own has **Yes** and **No**.
- **Any other answer**, used for an answer that has no version of its own.

A dynamic attribute has a version for every option. In a logic block, the settings list the attribute's answers under **Answers with their own content**, and only the answers that are ticked have a version of their own. **Add a version for another answer**, at the foot of the block, opens the settings so that you can tick another answer.

For example, a Per Alter Form could contain a logic block whose versions depend on a "Lives with you" attribute:

| Version          | Content                                      |
| ---------------- | -------------------------------------------- |
| If not known     | How often do you see them at home?           |
| Yes              | How do you share household tasks with them?  |
| No               | How often do you visit them at home?         |
| Any other answer | (empty, because yes and no cover every case) |

A categorical answer can include several options. The string then uses the version of the first of those options that has one, in the order in which the attribute's options are listed in the codebook, or **Any other answer** if none has one. Reordering the options in the codebook can therefore change which version is used.

## Wording for singular or plural numbers

This logic is intended for text in which the words around a number change with the number, as in "1 child" and "3 children". It can be chosen for a number or scalar attribute. It has an **If not known** version, used when there is no answer, and one version for each grammatical number form that the language distinguishes. English has two:

| Version               | Text written           | Participant sees |
| --------------------- | ---------------------- | ---------------- |
| When it is 1          | the number, "child"    | 1 child          |
| When it is 0, 2, 3, … | the number, "children" | 3 children       |

In a dynamic attribute, these versions are written together, under **If known**, and each can show the number as a pill. In a logic block, each number form is a version of its own, labeled with examples of the numbers that use it. To show the number there, insert the attribute itself.

Other languages distinguish a different number of forms: Chinese has one, and Polish and Russian have more than two. When the wording of a dynamic attribute is written in another language, in the stage editor or in the translation table, there is one box for each number form of that language, and each box already shows the number as a pill. A logic block with **Content for singular or plural numbers** in the text of another language has a version for each number form of that language.

## Wording for the participant or someone else

A Family Pedigree's form asks the same questions about the participant and about each of their relatives. In that form, a dynamic attribute or a logic block can use **Participant or someone else**, which has two versions:

| Version               | Text written              |
| --------------------- | ------------------------- |
| About the participant | What is your first name?  |
| About someone else    | What is their first name? |

Whether a question is about the participant is always known, so this logic has no **If not known** version.

## How participants see piped text

During the interview, each value is shown in the participant's language:

- A date is written in the format that the participant's language uses for dates. A date answer recorded only as a month or a year shows only the month or year.
- A number is written in the format that the participant's language uses for numbers.
- An answer to a categorical, ordinal or boolean question is shown by the option's label, in the participant's language. A label without a translation in that language is shown in the same way as any other [translatable string that has no translation](/en/design-protocols/tutorials/translating-your-protocol#the-default-language-and-which-translation-participants-see). An answer with several options is shown as a list, such as "cats, dogs and fish". A yes-or-no answer can be shown in this way only when both of its answers have labels; otherwise, use **Different wording for each answer**.
- A text answer is shown exactly as it was entered.
- Logic itself is never shown. The participant sees only the version that applies: the wording of a dynamic attribute, or the content of a logic block's version.

Each value is tinted with the interview's primary color. The tint distinguishes inserted information from the fixed wording of the question. Screen readers read the value as part of the sentence.

![The interview preview showing a Per Alter Form for a university node. The question reads "Did you visit Universidad Francisco Marroquín or study there?", with the university's name tinted.](/assets/img/piped-text/interview-preview.png 'The piped node label as the participant sees it')

[Preview mode](/en/design-protocols/preview-mode) is the most direct way to check piped text before fieldwork. With **Start preview with example data** switched on, the preview fills each value from generated data, as in the image above.

Where the table above lists every attribute of the node or edge that a form asks about, the question and hint of a field can show any of these attributes, including attributes collected on earlier stages and the attribute that the field itself collects. When the attribute has no value yet, nothing is shown in its place. In a form, a node's label in a question or hint updates as the participant types, in the same way as the label drawn on the node.

On an edge form, the labels of the two nodes that the edge joins are offered as **First node: label** and **Second node: label**. Their other attributes are not offered, because the nodes at either end of an edge can be of any type.

Some translatable strings never accept piped values:

- stage names
- image descriptions, because they stand in for an image
- strings in the codebook, such as the labels of options
- the [wording supplied by Network Canvas](/en/design-protocols/tutorials/translating-your-protocol#words-network-canvas-supplies), apart from a Family Pedigree's name for the participant. Some of this wording can show values that the interview fills in, such as the name of the stage's node type or a number, but not attributes

In a protocol upgraded from schema 8, braces that were already present in the text remain ordinary characters. They never become piped values.

## Translating strings that show values

When a protocol is offered in more than one language (see [Translating Your Protocol](/en/design-protocols/tutorials/translating-your-protocol)), each language has its own localized strings. Showing a value is optional in every language, so a translation can show more, fewer or different values than the localized string in the default language, or none at all. In the same way, a translation can use a dynamic attribute that the default language does not use, or leave out one that it uses, and in a translatable string of several lines, each language has its own logic blocks. Nothing in the protocol compares the localized strings of one language with those of another.

Each translation is checked on its own, by the same rules as the localized string in the default language: every value that it shows must be one that can be shown where the string appears, and at least one version of the string must not be blank.

The logic of a dynamic attribute is the same in every language: its logic option, its rules or its attribute, and the answers that have versions. Only the wording of each version is translated. To translate it, open the stage, choose the language in the text field's language menu (see [Translating within the stage editor](/en/design-protocols/tutorials/translating-your-protocol#translating-within-the-stage-editor)), and select the dynamic attribute's pill. Its settings show each version in that language, with the version in the default language beneath it for reference. In the translation table, the wording of each version has a row of its own. The row's name starts with "Dynamic attributes", then shows the dynamic attribute as a list of the wording of its versions, and ends with the name of that version, such as "Dynamic attributes › their / her / his › Woman".

Each language has its own logic blocks, but the rules of a logic block are saved with the stage, in the same way as the logic of a dynamic attribute. A dynamic attribute or a logic block can be added to a translation, and its logic can be changed, in the stage editor after you choose the language in the text field's language menu, or in that language's cell of the translation table. A change to the logic applies in every language that uses the dynamic attribute or the rules.

In the translation table, a cell shows values and dynamic attributes as pills. An open cell has the same **Attribute** and **Logic block** controls as the stage editor. A change to the logic is saved when the translations are saved. At that point, a dynamic attribute that no translatable string uses any more is removed, as it is when a stage is saved. The text of a form can also be edited in the table (see [Editing translations](/en/design-protocols/tutorials/translating-your-protocol#editing-translations)).

The values themselves are not translated. Dates and numbers follow the participant's language, and answers are shown with their options' labels in that language.

## Problems reported by Architect

Protocol validation checks every translatable string that contains piped values or logic. Each problem below is an error. The stage cannot be saved, and the protocol is not valid, until the error is corrected.

Architect shows the message beneath the text field, or in the cell of the [translation table](/en/design-protocols/tutorials/translating-your-protocol#the-translation-table). These messages are in English, whichever language Architect is set to.

### Problems that you can encounter while editing

These problems can arise from editing a translatable string in Architect, from pasting text that was copied from another field, or from changing the codebook or the stage after the string was written.

| Message                                                                                                                                                                                                  | What it means                                                                                                                                                                                                                                                                                                                                                                                  | How to fix it                                                                                                                                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **This wording cannot be blank in every version: at least one of its versions must show some words or a value.**                                                                                         | The string has no wording outside its versions, and every version is empty, so the participant would never see anything.                                                                                                                                                                                                                                                                       | Write wording in at least one version, or delete the logic from the string.                                                                                                             |

| **A logic block cannot depend on a field inside it, because the field is shown only when the logic block shows it.**                                                                                     | The rules or the attribute of a logic block in a form test the answer to a field that is inside the same logic block.                                                                                                                                                                                                                                                                          | Move the field out of the logic block, or change the logic block's rules.                                                                                                               |

### Reasons a value cannot be used

A message names a value in the way that Architect shows it to you. It names an attribute by its name and by the participant, node or edge that the attribute belongs to, such as **the "nickname" attribute of the node this stage is about**. It names other values as **today’s date**, **the label of the first node of the pair**, **whether the node is the participant**, **a dynamic attribute** or **a logic block**. It names the rules of a logic block whose logic is **If … else** or **If not … else** as **a logic block**. In a node type's dynamic label, the message begins **This label** in place of **This wording**. The message is one of these.

| Message                                                                                                                                                             | What it means                                                                                                                                                                   | How to fix it                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **This wording cannot use the "nickname" attribute of the node this stage is about, because the wording does not refer to that node.**                              | The value belongs to a node or edge that this string does not refer to. The message says which one, such as **the first node of the pair** or **the edge this stage is about**. | Delete the pill, then insert a value that the **Attribute** list offers for this string.                                                          |
| **This wording refers to an attribute that no longer exists.**                                                                                                      | The attribute is no longer in the codebook, or the stage now asks about a different node or edge type.                                                                          | Delete the pill, then insert another value if the string needs one.                                                                               |
| **This wording cannot use the "nickname" attribute of the node this stage is about, because the attribute is encrypted.**                                           | The attribute was made encrypted after it was piped. Encrypted attributes are never offered for piping.                                                                         | Delete the pill, or stop encrypting the attribute.                                                                                                |
| **This wording chooses between versions by the "pets" attribute of the participant, but one of its versions is for an option that no longer exists.**               | A logic block of the string has a version for each option of an attribute, and one of these versions is for an option that has since been deleted from the attribute.           | Delete the logic block from the string, then add a new one, which has versions for the attribute's current options.                               |
| **This wording refers to a dynamic attribute that no longer exists.**                                                                                               | The dynamic attribute has been removed from the stage.                                                                                                                          | Delete the pill.                                                                                                                                  |
| **This wording has a dynamic attribute that**, followed by a reason, or **This wording has a dynamic attribute whose rules are about**, followed by a node or edge. | The dynamic attribute depends on something that this string cannot use, such as an attribute of a node that the string does not refer to.                                       | Delete the pill, then use a dynamic attribute whose logic this string can use.                                                                    |
| **This wording has a logic block whose rules are about the first node of the pair, which this wording does not refer to.**                                          | The rules test a node or edge that this string does not refer to. The message says which one. This happens when a logic block is pasted into another string of the same stage.  | Delete the logic block, then add a new one in this string. Its rule builder offers only the rules that this string can use (see [Rules](#rules)). |
| **This wording cannot use whether the node is the participant, because this is known only in the questions of a Family Pedigree stage’s person form.**              | Logic with **Participant or someone else** was pasted into a string that is not part of a Family Pedigree's form.                                                               | Delete the pill or the logic block.                                                                                                               |

### Problems in a protocol edited outside Architect

Architect's editor does not write strings that break the rules below. These errors arise only when a protocol file has been changed by hand or by another program. Architect reports them when it opens or checks the protocol.

To fix any of them, go back to a copy of the protocol that Architect saved, or correct the file in the program that changed it.

In schema 9, a form is written as one piece of formatted text, and text can contain logic blocks and dynamic attributes.

**Forms.** The form of an Ego Form, Per Alter Form, Per Alter Edge Form, Name Generator (using forms) or Family Pedigree stage is written in Architect's text editor, under **Form content**. Each question is a field: a block in the text, placed where the question is asked, which shows the question, its hint and its input control as participants will see them. **Field** in the toolbar adds a field and opens a list of attributes at the **Field** button. Ctrl+Shift+F (⌘+Shift+F on a Mac) also adds a field, and opens the list beside the new field. To create an attribute, type its name, choose **Create “…”**, and then choose the type of answer that it records; the input controls offered for a field are those for its attribute's type. Selecting a field opens its settings beside it: its attribute, input control, options and validation, **Show validation hints**, and **Delete field**. Headings, paragraphs, lists, images, audio and video can come before, between and after the fields. A field can be dragged by its handle, or moved with Ctrl+Shift+Up arrow and Ctrl+Shift+Down arrow. Every form must contain at least one field. A Name Generator's form keeps its **Dialog title**. The forms of a Network Composer stage are unchanged.

**The Ego Form introduction.** An Ego Form no longer has an introduction panel. A heading and text at the top of its form take its place.

**Logic blocks.** Text of several lines, such as an Information page, the explanation on an Anonymisation stage, the text of a Finish Screen and a form, can contain logic blocks, added with **Logic block** in the toolbar. A logic block shows different content in different cases: when rules are met or not met, for each answer to an attribute, for singular or plural numbers, or, in the form of a Family Pedigree stage, for the participant or someone else. Its versions can contain any content, including further logic blocks, and in a form they can contain fields. During the interview, a form shows the fields of the versions that apply, and it changes as the participant answers. When the participant submits the form, the answers to fields that logic hides are cleared. While a field is hidden, it has no answer: a validation rule that compares an answer with it, such as **Same as another attribute**, does not use the answer that was recorded before. In a form, the attribute lists of a logic block's settings show the attributes that the form's fields collect first, under **Answers on this form**, and then those recorded before the form, under **Answers from earlier stages**. An attribute that only a field inside the block collects, or only a field in another version of a logic block that contains the block, is listed but cannot be chosen. A protocol in which a logic block depends on such a field is refused.

**Dynamic attributes.** The **Attribute** button in the editor's toolbar, or typing `{`, inserts a value. A word or phrase inside a sentence that reads differently in different cases is now a dynamic attribute: choose **Create dynamic attribute** in the list of attributes, choose its logic and write its versions. A dynamic attribute belongs to its stage, or to the node type in a dynamic label, so it can be used in more than one translatable string, and a change to it applies everywhere that it is used. Dynamic attributes replace the logic that was written inside a sentence.

**Missing values.** A value that is missing shows nothing. Architect no longer asks for wording to show when a value is missing. To show different wording when a value is missing, use a logic block with a rule that the attribute **exists**, or the **If not known** version of a dynamic attribute or logic block that has a version for each answer. In the rules of a logic block, a dynamic attribute or a dynamic label, a rule about an attribute of the participant, a node or an edge now offers **exists** and **does not exist**, which check whether the attribute has an answer. These rules use the same definition of a missing value as piped text: text that is empty or contains only spaces, and a categorical answer with no options selected, count as missing. The rules of skip logic and filters are unchanged.

**Languages.** Each language has its own form, and the forms in different languages can contain different fields. A field that is in the forms of two languages is the same field, and only its question and hint are translated. When the form in the language that you are editing contains different fields from the form in the default language, a note above the editor names them. The logic of a dynamic attribute is the same in every language, and only the wording of its versions is translated.

**The translation table.** The text of a form can be edited in the translation table, with its fields shown as blocks. The question and hint of each field are shown in the language of the cell and translated in rows of their own. **Field** lists only the form's own fields, so that a field from the form in another language can be added. Removing a field from one language's text also removes its question and hint in that language, and a change that would leave a field out of the form in every language cannot be saved. Logic blocks and dynamic attributes can be added and changed in any cell, as in the stage editor. The wording of each version of a dynamic attribute has a row named after the dynamic attribute's versions and then the version, such as "Dynamic attributes › their / her / his › Woman", and wording for singular or plural numbers opens with one box for each plural form of the cell's language. Copying the whole content of one language's cell to another copies its fields, logic blocks and dynamic attributes with it. Fields that are copied from the translation table into a stage editor take their questions and hints in the language that the stage editor shows. When a stage or the translation table is saved, a dynamic attribute that no translatable string uses any more is removed.

**Upgrading from schema 8** turns each form into one piece of text, with its fields in the order in which the form showed them, and turns the introduction panel of an Ego Form into a heading and text at the top of its form.

- `@codaco/protocol-validation`: a schema 9 form is `{ content, fields }`. `content` is a localized string of several lines that places each field as `![](field:<id>)`, in a paragraph of its own. A `select` or `plural` is allowed only as a logic block: a whole block of a string of several lines. Stages and dynamic node labels take `dynamicAttributes`, which text names as `{dynamic_<id>}`. New exports read and print these documents (`readContentDocument`, `printContentDocument`, `fieldBlockMarkdown` and others), describe the logic of a logic block and of a dynamic attribute with one type (`Logic`, with `logicOfDynamicAttribute` for a stored dynamic attribute), choose the version that logic shows (`chooseVersion`, `shownFieldIds`), list what logic reads (`logicReads`) and its versions (`logicVersions`), and check them (`findContentDocumentTextProblem`, and `findDynamicAttributeProblems` for the dynamic attributes of stages and node labels). `findDynamicAttributeProblems` reports a version that has no wording in any language in each language that shows the dynamic attribute. A link reference definition (`[label]: address`) applies to links in every block of a document, as the interview reads it, so a definition whose address or title contains a value is refused, as a link whose address contains one is.
- `@codaco/fresco-ui`: the rich text editor can contain field blocks, logic blocks and inline value pills. With `insertTools: { label, render }`, the host draws its own toolbar controls, which add values and blocks: `render` draws them, and `label` names their group in the toolbar. Typing `{` asks the host's controls for a value at the caret. `render` is given a `RichTextInsertState`: the editor's commands, and whether a block can be added at the caret. The `commandsRef` prop gives the host the same `RichTextCommands`, an object that stays the same while the editor is mounted, for changes that are made from outside the toolbar: `insertContent` adds inline content such as a set of versions, `removeInlineValues` removes every use of a value as one change that can be undone, and `returnFocus` returns the keyboard to the text when the host's list closes. A field block contains its question and hint as text that is typed in the block, or, with `fieldBlocks.text: 'none'`, contains no text and is one unit that the caret moves past. `fieldBlocks.textOf` gives the question and hint of a field that is pasted without them. The view of a logic block is given `fieldScope()`, which lists the fields inside the block, the fields in other versions of the logic blocks that contain it, and the other fields of the document. It is also given `branchesWithContent()`, the keys of its versions that are not empty. With `versions`, a piece of text that is nothing but one set of versions shows them open, one labelled row each. `ValidationContext` takes `formVariables`, the variables that the form's fields collect: a validation rule that compares with one of them uses only the form's value, so while that field is not mounted the rule has nothing to compare with, and the stored value is not used. `SelectOption` gains `description`, a sentence shown under an option's label in the styled select. A dialog opened through `useDialog` takes `dataAttributes`, which are put on its popup. The package adds the `./interfaceLanguage` export, and `./hooks/useFocusWithin`, which follows whether focus is in an element or in a popup that it opened. Breaking changes:
  - The editor's `tokens`, `insertMenu` and `logicMenu` props are removed, and so is `TokenPill`. A value in the text is stored as `{ type: 'inlineValue', attrs: { id } }` instead of `{ type: 'token', attrs: { id } }`. The editor cannot read a stored `token` node: a document that contains one opens empty, and the next edit saves the empty document over it. Convert stored documents before upgrading.
  - Popups are drawn in a new order. The positioners of `Popover`, `DropdownMenu`, `Tooltip`, the styled `Select` (previously `z-50`) and `Combobox`, and the portal of each `Modal`, carry `z-3000`, so the popup opened most recently is drawn on top. A `Popover`, `DropdownMenu` or `Select` that stays mounted while it is closed moves its portal node to the end of its container each time that it opens. The toast viewport carries `z-3001` (previously `z-10`), so toasts are drawn over every popup and dialog. Content that an app draws over popups needs a z-index above `z-3000`.
- `@codaco/network-query` exports what logic reads and how conditions are tested (`logicInputsFor`, `readDynamicValue`, `conditionMet`, `conditionHolds`, `conditionReadsNetwork`, `buildConnectivityIndex`), which the interview previously kept to itself. The interview and synthetic data both use them.
- `@codaco/shared-consts` exports `isUnanswered`, the one definition of an empty answer.
- `@codaco/protocol-utilities`: `SyntheticInterview` writes each form as a document (`form.content`) and takes `dynamicAttributes`. It no longer takes `introductionPanel`; a form takes `content`, written from its field blocks. `generateNetwork` takes `formLanguage`, the language that the participant reads, and answers only the fields that the form in that language shows, leaving out fields that it does not contain and fields that logic hides. An Ego Form's synthetic answers are drawn only for the attributes that its fields collect.

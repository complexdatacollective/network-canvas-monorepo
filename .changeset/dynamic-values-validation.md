Schema 9 stage text can show values from the interview, such as the participant's name, an attribute of the node that a question is about, or today's date. Each argument of a message names the value that it shows directly, by id, so a protocol stores no separate list of values. The argument for an attribute is the role whose attribute it is, followed by the variable's id: `{ego_<id>}` for the participant, `{node_<id>}` and `{edge_<id>}` for the node or edge that a form describes, `{dyadSource_<id>}` and `{dyadTarget_<id>}` for the two nodes that a Dyad Census asks about, and `{focal_<id>}` for the focal node of a one-to-many census. Each of those nodes can also be shown by its label (`{node_label}`, `{dyadSource_label}`, `{dyadTarget_label}`, `{focal_label}`), as can the two nodes that an edge form's edge joins (`{edgeFrom_label}`, `{edgeTo_label}`). The label is the text that the interview shows on the node, chosen by its label rules and falling back to "Unnamed" in the participant's language, so it is never missing. `{now}` is today's date. A message's argument names and select keys cannot contain `-`, so every `-` of an id is written as `_`; a UUID never contains `_`, so the change can be undone. The id in a name must be a whole UUID written this way, so a name such as `ego_first_name` refers to nothing. Renaming an attribute changes no message.

A message can give a version for each answer to a categorical or ordinal attribute, keyed by the option's id (`optionCaseKey`). An answer matches an option as the schema compares option values, so an answer of `"1"` is the option whose value is `1` (`isSameOptionValue`). A categorical answer that includes several options chooses the first of them, in the codebook's order of the options, that the message has a version for. A yes/no attribute's versions are keyed `true` and `false`.

- Prompts, form field captions, introduction and panel text, Information screens (but not image descriptions), the anonymisation explanation and the finish screen's heading and text may show values. Stage labels, codebook text, `interfaceText` and wording Network Canvas supplies may not.
- Each site shows only what is available there: the participant and today's date everywhere, the pair on a Dyad or Tie Strength Census prompt, the focal node on a one-to-many census prompt, the node being placed on a Geospatial prompt, and on a form field every attribute of the form's subject, including the question a Categorical Bin asks about a node put in its "other" bin. An edge form's fields, a Network Composer edge type's included, also show the two nodes the edge joins, by label only. `dynamicValueContextFor`, `dynamicValueArgumentsAt` and `dynamicValueStatus` give that table, and `findDynamicValueProblems` checks a protocol against it.
- An attribute can always be missing, so it is shown only inside a version for when it has one: `{ego_<id>, select, missing {…} other {…{ego_<id>}…}}`. Versions can also follow a value's cases or, for a number, its plural category, chosen by the number with every digit it is shown with. `findDynamicValueProblem` is the one checker, given the argument or the problem for each name that the text uses (`DynamicValueLookup`) and the text's language; text whose every version the values can reach shows nothing is refused. `dynamicMessageParts` gives the version a message reads for given values.
- Every language's text is checked on its own, by the same rules. Showing a value is optional, so a translation may leave out a value the default-language text shows; where a field requires an argument, it requires it in every language, the default included.
- An argument that names no attribute, condition or role, an attribute that is encrypted, a version for a case that the value does not have, and a value that cannot be shown where the text is are each an error in every translatable string that uses them.
- Each problem names a value as a researcher knows it: an attribute by its name and whose it is (`the "Age" attribute of the participant`), and otherwise as "today’s date", "the label of the first node of the pair", "whether the node is the participant" or "an If block". A problem never shows an argument name, an id or a case key, except an argument name that refers to nothing, which is quoted as it is written. A name that refers to something that is gone says so: "This text refers to an attribute that no longer exists.", "This text has an If block whose rules no longer exist." and "…, but one of its versions is for an option that no longer exists." `DynamicValueArgument` gains `description`, the words that these problems use for the value.
- Text shows a yes/no attribute by its options' labels, so it can show one as words only when the attribute has a label for both yes and no; otherwise the text is refused with a message naming the attribute and asking for the labels (`dynamicValueUnshowableReason`). Text may still choose its wording by any yes/no attribute, including a Toggle, which never has labels. The attributes that a message names count as uses of them in `collectEntityAttributeReferences`, which reports each as `inMessage`, with the options that the message gives versions for. When an option is removed from an attribute, Architect removes the versions of text written for it.
- Interview metadata (IDs, start time, protocol name or hash, stage ID) is deliberately not available.
- Text cannot contain U+E000, which the interview uses to place values (`DYNAMIC_VALUE_MARKER`).
- `parseDynamicValueName` reads an argument name, `dynamicValueNameFor` writes one, `dynamicValueReferencesIn` lists the names and case keys that a message uses, `rewriteDynamicValueReferences` renames them, `dynamicValueCaseOf` gives the case that an answer chooses, and `findSiteMessageProblem` checks one message at one site.
